## Report: F42 Marketplace plans

- **Status:** Done (awaiting merge). The Verification items that need a draft listing stay open, see "Verification".
- **Summary:**
  - A `marketplace_account` record per GitHub account ID holds the Marketplace plan ID, the billing cycle, the trial end, and the pending plan with its effective date. It belongs to no tenant.
  - `marketplace_purchase` arrives at `/webhook/github`. The consumer queues the tenantless `MarketplacePurchaseJob`: `purchased` and `changed` replace the record and clear the pending change, `pending_change` stores the pending plan, `pending_change_cancelled` clears it, and `cancelled` deletes the record.
  - Each GitHub sign-in reads `GET /marketplace_listing/accounts/{id}` with the App JWT for the user account and each installation account: a 200 replaces the record, a 404 deletes it. `GitHubInstallation` and `AccountPayload` have the account ID.
  - The plan of a tenant is the plan with the highest rank among those accounts, else the free plan. `UsageLimits` takes its limits from it. `Me.plan` and the Settings section "Plan" show the name, the trial end, the pending change, and the listing link.
  - `cancelled` of a user account also queues `MarketplaceCancellationJob` for the tenant of that user, delayed by 30 days. It reads the plan again and purges the tenant through `DeletionHandler::purge()` when GitHub answers 404 and the tenant has no installation left, of any account.
- **Plan configuration**, so the plans of the listing need no code change:

  | Variable | Parameter | Value |
  |---|---|---|
  | `APP_PLAN_FREE_*` (F39) | `app.plans.free` | The limits of the free plan, rank 0, name "Free" |
  | `APP_PLAN_FREE_MARKETPLACE_PLAN_ID` | `app.plans.free.marketplace_plan_id` | The Marketplace plan ID of the free plan of the listing. Empty: none. |
  | `APP_PAID_PLANS` | `app.paid_plans`, `%env(json:default::...)%` | A JSON object by plan key, each with `name`, `marketplace_plan_id`, `rank` of at least 1, and the five limit keys of F39. Empty: no paid plans. `App\Application\Plans` checks each entry and fails with the name of a wrong one. |
  | `GITHUB_MARKETPLACE_URL` | none, read by `MeController` | The listing that Settings links. Empty: `listingUrl` is null. |

- **Decisions and deviations:**
  - Plans: the free plan stays in `app.plans.free` with the F39 variables, and the paid plans come from one JSON variable `APP_PAID_PLANS` in `app.paid_plans`, so the listing plans, which do not exist yet, need no code change. A YAML parameter cannot merge a JSON variable into `app.plans`, so there are two parameters. The free plan has its own `APP_PLAN_FREE_MARKETPLACE_PLAN_ID`, so a purchase of the free plan of the listing logs no error.
  - `APP_PAID_PLANS` refuses two paid plans with one rank, because the plan of a tenant would then depend on the row order of the records.
  - Plan names come from the configuration, not from GitHub, so the name always matches the limits that apply. The free plan is "Free".
  - `Me.plan` also has `listingUrl`, the value of `GITHUB_MARKETPLACE_URL`, because the UI reads it from A1. Times are `trialEndsAt` and `pendingChange.effectiveAt`, as the other times of the specs. Settings formats them as UTC dates, because GitHub sends UTC midnight.
  - The record is written with raw SQL `INSERT ... ON CONFLICT` in `MarketplaceAccountSql`: GitHub sends `purchased` and opens the Setup URL at the same time, so the delivery and the sign-in write one account at once. The entity has no repository, as `WebhookDelivery`.
  - The trial end is stored only while `on_free_trial` is true. `pending_change` and `pending_change_cancelled` change only an existing record: without one, the next sign-in reads the plan. A pending change without a plan, or with a plan ID the instance does not map, shows the free plan.
  - An unknown plan ID logs the error at each plan resolution, so the misconfiguration stays visible until `APP_PAID_PLANS` names the plan.
  - The webhook consumer routes a job with a null tenant without a `TenantStamp`. The cancellation job is an `Envelope` with a `DelayStamp` of 30 days in the job list of the consumer, so the inactive-tenant filter applies to it too.
  - The cancellation job purges with `DeletionHandler::purge()` directly, as `app:tenant:purge` does, without the A2 mark, because the job already runs in the worker. The installation count runs as the `keep` guard of `purge()`, inside the delete transaction after the tenant row lock `FOR UPDATE`. Every installation write holds that row `FOR SHARE` through `GitHubRepositoriesLock::run()`, so a write that started first has committed before the count, and a write that starts later waits and then finds the tenant gone. A test of the race needs two database sessions, so no test provokes it.
  - A failed plan read at the due time throws `RecoverableMessageHandlingException` with a retry delay of one hour and `forceRetry: true` (Symfony 8.1), so Messenger retries the job every hour without the limit of 3 retries of the `async` transport, and the purge is decided only on an answer of GitHub. A new dispatch with a `DelayStamp` would do the same with a new message per hour.
  - Purge rule, a review decision of 2026-10-13: the job purges only when GitHub answers 404 for the user account and the tenant has no installation left, of any account. The scope and D65 said "no installation on that account", which purged a user who cancelled the own plan and still works through an organization installation. D65, the spec, and `docs/user/getting-started.md` say so.
  - The sign-in reads the Marketplace plans only after a successful installation listing. A failed listing returns before it, as before.
  - Fixtures: Team 1111 with rank 1 and Pro 1313 with rank 2 in `.env.test`, from the plan IDs of the GitHub REST example.
  - `MarketplaceAccountSql::replace()` takes plain values, not the GitHub payload, so `Repository` does not depend on `GitHub`, which would close a namespace cycle through `Entity`.
- **Follow-ups and new ideas:**
  - A second `cancelled` of the same account within 30 days queues a second job, and the first one decides on the date of the first cancellation. GitHub sends `cancelled` at the end of a billing cycle, so this needs a purchase and a cancellation inside one trial.
  - The sign-in reads the accounts one after the other. A tenant with many installation accounts could read them concurrently through the asynchronous responses of the HTTP client.
  - The developer guide listed `Domain, Entity` as the dependencies of `App\Message`, but `GitHubPullRequestJob` of F40 already imports `App\GitHub`. The row now names `GitHub`.
