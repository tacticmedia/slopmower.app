## Report: F14 Pull request links

- **Status:** Done (awaiting merge). One commit `feat: F14 pull request links` on the worktree branch, rebased on `45d8a9e`, after F13 (`dca8362`).
- **Summary:**
  - Q17 `POST /api/v1/pull-request-links` with `{url, requestIds, note?}` and the MCP tool `link_pull_request` (section 4.14) return a `LinkPullRequestResult` `{url, requests, events}`.
  - An agent links a pull request to requests that it holds while they are `in_progress`, or to requests that are `ready_for_review`, which any agent may link because `request.ready_for_review` clears the claim. On an `in_progress` request the proposal gate of F13 applies, as for `link_commits`. The rule is `Action::LinkPullRequest => $isAgent && (($holds && $proposalGateOpen) || RequestStatus::ReadyForReview === $status)`.
  - `PullRequestUrl`: `https`, at most 2,048 characters, no whitespace. On a GitHub repository, `PullRequestUrl::forRepository()` also requires `https://github.com/{owner}/{name}/pull/{number}` of the review's repository, compared case-insensitively, and returns the canonical form `https://github.com/{repository}/pull/{number}` with the repository name as connected. `RequestCommands::linkPullRequest()` passes the repository name in the `LinkPullRequest` command, so `RequestDecider` reports the URL and `requestIds` violations together.
  - Event `pull_request.linked {url, requestIds, note}` with a null `requestId` column. The reducer appends to `RequestState.pullRequestUrls`, projected to the jsonb column `change_request.pull_request_urls`, so a rebuild recomputes it. It updates `lastEventSeq` and `updatedAt`, not the agent tracking, so `awaiting` never flips. Pairs that are already linked are skipped, and no new pair writes no event.
  - UI: the request detail header lists "Pull requests", and the thread shows "linked a pull request" with the link. Both open in a new tab with `target="_blank" rel="noreferrer"`.
