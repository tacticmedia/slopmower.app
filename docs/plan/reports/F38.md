## Report: F38 Database connection parameters

- **Status:** Done 2026-10-09.
- **Summary:**
  - The Doctrine connection `default` takes `DATABASE_HOST`, `DATABASE_PORT`, `DATABASE_NAME`, `DATABASE_USER`, `DATABASE_PASSWORD`, `DATABASE_SERVER_VERSION`, and `DATABASE_SSLMODE` without the `resolve:` processor. `DATABASE_URL` is gone, so a raw RDS master password needs no encoding.
  - Both Messenger transports use `doctrine://default` with `auto_setup=0` in `config/packages/messenger.yaml`. `MESSENGER_TRANSPORT_DSN` is gone, so the queue always goes through the DoctrineBundle connection and its RDS middleware.
  - On Jan's request, the advisory lock store uses `default` too, and the connection `lock` of F28 is gone. Each PHP process has one database session.
  - The host port of the compose database is `DATABASE_PUBLISHED_PORT`, and its act override `ACT_DATABASE_PUBLISHED_PORT`.
  - Mate and the lock test helper build their connections from the same variables.

    - "A raw password with URL-reserved characters signs in": a role with the password `p%%a%s#s?w$o\r&d;=!1` signs in through `doctrine.dbal.default_connection`, and `current_user` is that role. With `%env(resolve:DATABASE_PASSWORD)%` the test fails with `password authentication failed`. The role is dropped in `finally`, also after a failure.

- **Decisions and deviations:**
  - Locks on `default`: Jan asked during the work whether the locks can reuse the connection. They can. `DoctrineDbalPostgreSqlStore` keeps an in-memory store per connection object, every lock uses the non-blocking `acquire()`, and every transaction owner rolls back before a lock is released. An aborted transaction refuses `pg_advisory_unlock`, so the plan README gotchas and `config/packages/lock.yaml` state that rule.
  - `failed` also gets `auto_setup=0`. The migrations own `messenger_messages`, so neither transport creates it.
  - An uncommitted `.env` edit in the main checkout had moved `DEFAULT_URI=http://localhost` into the comment line above it, so the variable was gone. F38 restores that line as on `main`.
- **Versions:** `tacticmedia/rds-auth-bundle` stays at 1.1.2 with `tacticmedia/rds-auth-middleware` 1.1.3. The bundle 1.2.0 of 2026-10-09 requires the middleware ^1.2, which has no tag on GitHub and no release on Packagist, so Composer cannot install it. The F38 configuration follows the 1.2.0 documentation. The driver of the middleware on `main` reads the same parameters, and also treats an empty `sslmode` or `port` as unset.
- **Follow-ups and open questions:**
  - For Jan: release `tacticmedia/rds-auth-middleware` 1.2.0, then `composer require tacticmedia/rds-auth-bundle:^1.2`.
  - The RDS bundle has one `iam_username` for every connection. The three database roles of [database-hardening.md](../../backlog/database-hardening.md) need a user per connection in IAM mode.
- **Risks discovered:**
  - The raw-password test creates a role, so the test database user needs `CREATEROLE`. The compose `POSTGRES_USER` is a superuser. The roles of database-hardening.md would change that.
  - A checkout whose `.env.make.local` still exports `DATABASE_PORT` publishes the database on 5432 again. Rename it to `DATABASE_PUBLISHED_PORT`.
