- **Decisions and deviations:**
  - **Deviation, unit test scope.** The unit test has one case per row of the table and per bullet that the pure function decides. Two bullets need stored rows and have their case in `IssueToolsTest`: "a plan with new text clears `planApproval`" is `Issue::changeSection()`, and the link rules read the stored pair.
  - **Deviation, `docs/specs/mcp.md` section 1.** The scope names sections 2 to 6. Section 1 quotes `config/packages/mcp.yaml`, so its `description` line changed with the file.
  - **Deviation, docs.** `docs/architecture.md` sections 4, 7.3, and 7.7 changed next to section 3, because they named 18 tools, one skill, and the scope of a repository token.
  - **Single-consumer rule.** `IssueCommands` and `IssueQuery` have one consumer, `McpTools`, until the REST controllers exist, as the scope file decides.
  - **Feature brief.** `.claude/orchestration/feature-brief.md` is git-excluded and not in the worktree. It was read from the main checkout.
  - **Entry shape.** `IssueEntry` is flat like `ThreadEntry`: `id`, `kind`, `actor`, `createdAt`, `body`, `section`, `from`, `to`, `note`, `reviewer`, `reviewNote`, `planRevision`, with null for the fields of another kind. `kind` is an open set. A status change stores `note` in `data`, as the scope lists it. `get_issue` returns `body` only for a comment.
  - **Schemas.** `project.schema.json` is `Project`. `issue.schema.json` is `Issue`, with the definitions `PlanApproval`, `IssueSummary`, `IssueLink`, `IssueEntry`, and `IssueDetail` (`{issue, links, thread}`), the result of `get_issue`. `lists.schema.json` has `ProjectPage` and `IssuePage`, each `{items, nextCursor}`. A link shows the other issue as an `IssueSummary`.
  - **Limits.** `list_projects`: 1 to 500, default 100, as `list_repositories`. `list_issues`: 1 to 200, default 50, as `list_requests`. `reviewer`: 1 to 64 characters, as an agent name. Sections, notes, and comments: 65,536 characters.
  - **Order of `tools/list`.** The file and `McpTools` stay in alphabetical order, so the nine tools are between the others.
  - **Annotations.** `update_issue` has `idempotentHint: true`, because the same values change nothing, as `claim_request`. The other five writes have false.
  - **`create_issue.status`.** The input schema lists `draft`, `backlog`, and `todo`, so another status is -32602. `IssueRules` refuses it too, for a later caller.
  - **Refusal fields.** The field is the issue field or the input that breaks the rule: `problem`, `plan` (empty, not approved, or changed in `in_progress` or `in_review`), `result`, `status` (the same status, or `done` and `wont_do` in `user` mode), `reviewer`, `note`, `planRevision` (not the newest), `issue` (an ended issue, or `approve_plan` in `user` mode), `target` (the issue itself, or a second link), `''` for `update_issue` with no field. Each message says what to do next, for example "The plan needs an approval before in_progress. Let another agent review it, then call approve_plan."
  - **Check order.** A lookup comes first, so an invisible key answers `not_found` before any `invalid_input`. A status change to `done` or `wont_do` checks the approval mode, the reviewer, and the note before the sections.
  - **Write order.** A write changes the entities, flushes, and then checks the stored state, because the plan revision comes from the entries. A refusal rolls back and clears the entity manager, as `CommandExecutor` does. A refused `create_issue` takes no number.
  - **Entries of `create_issue`.** A `problem` writes a `section_changed` entry, so the first text is in the revision history. The first status writes no entry: `createdBy` and `createdAt` hold it.
  - **`approve_plan`.** A second approval replaces the first. It works in `self` mode, where nothing needs it. It is refused on an ended issue. `reviewNote` counts 20 characters after trimming.
  - **`allowedStatuses`.** The statuses that `set_issue_status` takes now when a note and a reviewer are given.
  - **Title.** The rules of a request title: trimmed, one line, 1 to 200 characters.
  - **`IssueLink`.** The primary key is the pair, with no ID class. The write locks both issue rows in key order and refuses the pair in the other order. No index covers the other order.
  - **`issue.plan_approval_id`.** `ON DELETE SET NULL`, because `issue` and `issue_entry` reference each other and the purge deletes the entries first.
  - **No repository class and no normalizer.** The lookups with the row lock are `IssueQuery::project()` and `issue()`, and every response class is schema-shaped.
  - **Migration.** `make migration` wrote it. The `down()` statements of `repository` moved before `DROP TABLE project`, because the generated order fails. `up`, `down`, and `up` ran on the dev database.
  - **`make issues-dump`.** It adds `--disable-triggers`, because `pg_dump` cannot order `issue` and `issue_entry`. It writes a `.part` file first, so a failed dump leaves no `.sql` file.
  - **Rebase on F125.** One conflict: the three ID classes moved from `config/packages/doctrine.yaml` to `config/packages/doctrine_types.php`. With `mcp/sdk` 0.9.0 an answer that does not match its output schema is an error, and every issue tool test passes as it is.
  - **Instructions.** 4,082 characters. The paragraph on issues has 238. The change-request text lost 218 characters by wording only: every numbered step, rule, and tool name is still there.
  - **Skills.** The first skill is unchanged. `ErrorCodeDocumentationTest` still reads only the first skill, whose table has every code.
  - **`clone` with properties.** `IssueState::withStatus()` uses the PHP 8.5 form. php-cs-fixer 3.95 writes it as `clone ($this, [...])`.
- **Follow-ups and new ideas:**
  - A project in `user` mode stops an agent at the plan until the web interface has the user approval. `IssueEntry::planApproved()` takes a reviewer and a review note, which a user approval does not have.
  - `list_issues` filters one status. The skill tells the agent to look through the open issues, which takes one call per status or every page. Idea: an `open` filter.
  - `get_issue` returns the whole thread. Idea: a page of entries when threads grow.
  - The second skill has no public route and the first skill does not name it.
  - `pg_dump --data-only` warns about the circular foreign keys of `issue` and `issue_entry`. A restore needs a role that can disable triggers.
  - `make fixtures` needs `APP_LOCAL_SIGN_IN` in the stack, which a worktree stack does not set by default.
  - The module counts of `docs/developer-guide.md` were off by one for `App\Application` before this feature.
