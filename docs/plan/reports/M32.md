## Report: M32 GitHub sign-in

- **Status:** Done (awaiting commit).
- **Summary:** `hwi/oauth-bundle` 2.5.0 is installed with contrib recipes allowed. The resource owner `github` has `options.csrf: true`, the client ID from `GITHUB_APP_CLIENT_ID`, and the secret from `%env(default::GITHUB_APP_CLIENT_SECRET)%`. The `oauth` authenticator is in the base `main` firewall, next to `LocalSignInAuthenticator`. `GET /connect/github` (route `hwi_oauth_service_redirect`) and `GET /login/check-github` (route `github_login_check`) have the route condition `env('GITHUB_APP_CLIENT_ID') !== ''`, so both answer 404 without a GitHub App, and the authenticator never sees its check path. `GitHubUserProvider` finds the user by `githubUserId` inside `TenantFilter::suspend()`, creates the tenant and the GitHub user at the first sign-in, and updates `login`, `name`, `avatarUrl`, and `lastSignInAt` later. `/login` shows "Sign in with GitHub" when the client ID is set. The session keeps a `PostAuthenticationToken`, not the OAuth token with the GitHub user token.

- **Deviations and decisions:**
  - `hwi_oauth.http_client` is an alias of the scoped client `github.client` (scope `^https://(api\.)?github\.com/`, timeout 10 s). The bundle builds its own client with `HttpClient::create()`, which `framework.http_client.mock_response_factory` does not reach. A framework client gets the mock factory and the profiler.
  - The resource owner `hwi_oauth.resource_owner.github` is not shared, through `Kernel::process()`. The resource owner keeps the `state` of a sign-in in its own properties and has no reset method. In a FrankenPHP worker, every user then got the same CSRF token in the `state` until the worker restarted, and the stored state of one user leaked to the next. `OAuthStateTest` proves the fix with a kernel that is not rebooted between requests, which resets services as the worker does.
  - `DropOAuthTokenListener` replaces the `OAuthToken` with a `PostAuthenticationToken` on `AuthenticationTokenCreatedEvent` of the `main` firewall. The session stores the authenticated token, and the `OAuthToken` serializes the GitHub user access token and refresh token. Architecture section 9 says that the server does not store the user token. A `LoginSuccessEvent` listener still reads the token from the `OAuthTokenBadge` of the passport, for M33.
  - Recipe routes: only the `redirect.php` import stays, with the route `hwi_oauth_service_redirect` at `/connect/{service}`. The imports of `connect.php` (`/connect/service/{service}`, `/connect/registration/{key}`) and `login.php` (`/login/`) are removed, because docs/specs section 7 does not list them and the "connect" feature is not configured. The check path route `github_login_check` is an attribute route on `SecurityController`, with a method that throws, as M10 writes the routes that an authenticator handles. The `oauth` firewall options keep their defaults for `use_forward` and `failure_path`.
  - The recipe variables `FB_ID` and `FB_SECRET` are replaced by `GITHUB_APP_CLIENT_ID` and `GITHUB_APP_SLUG`, empty. The secrets have no line in `.env`, because a `.env` value wins over the vault.
  - `.env.test` gets fake values only for what M32 reads: client ID, slug, client secret. `GITHUB_APP_PRIVATE_KEY` and `GITHUB_APP_WEBHOOK_SECRET` come with M33 and M34.
  - The GitHub fixtures are not recorded from a live App, because no App exists. They copy the documented GitHub responses: the form-encoded token response (HWIOAuthBundle sends no `Accept: application/json`), `GET /user` with `email: null`, and `GET /user/emails` with 403 "Resource not accessible by integration", which an App without the email permission gets. Each file holds `status`, `headers`, and `body`. `GitHubResponses` selects the `/user` fixture by the bearer token, so it keeps no state, and no test reads it from the container.
  - `OAuthStateTest` reads the outbound GitHub requests from the profiler's `http_client` collector.
  - `composer config extra.symfony.allow-contrib true` writes the string `"true"`. The project uses `--json`, so the value is the boolean `true`.
  - A failed GitHub sign-in redirects to `/login` through the HWIOAuthBundle failure handler, which stores no error in the session, so the page shows no message.
  - `GitHubUserProvider` turns a `/user` response without an ID or a login into an `AuthenticationException`, so it ends on `/login`, not in a 500. The fixture `user-unauthorized.json` is GitHub's 401 "Bad credentials".
  - Four tests beyond the acceptance list: the valid-state callback with the session check, the worker-mode state test, the `/user` response without an ID, and the second data set of the button test. Each proves one of our rules.
  - `LocalSignInGuardTest` uses the new `EnvironmentVariables` trait instead of its own save and restore code. It sets `GITHUB_APP_CLIENT_ID` empty, so it covers local sign-in without a GitHub App, and `LocalSignInStillDevOnlyTest` covers it with one.

- **Risks discovered:**
  - HWIOAuthBundle calls `GET /user/emails` at every sign-in when the profile has no public email. The App has no email permission, so the call gets 403 and the bundle ignores it. One extra request per sign-in.
  - A `_failure_path` query parameter with an absolute URL on `/login/check-github` makes the HWIOAuthBundle failure handler call the router with the URL as a route name: 500. A relative path redirects on the same host. No open redirect.
  - None from `_target_path`: the success handler honours it on the callback, but `security.http_utils` has the domain regex `{^https?://%s$}i` from `AddSessionDomainConstraintPass`, so `HttpUtils::createRedirectResponse()` sends a URL on another host to `/`.
  - Two simultaneous first sign-ins of one GitHub user hit the unique index on `github_user_id`, and one request gets 500.
