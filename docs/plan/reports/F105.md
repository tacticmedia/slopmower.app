## Report: F105 Next request on the request page

- **Status:** Done 2026-11-03.
- **Summary:**
  - `SplitDecisionButton`: a Primer `ButtonGroup` with the primary decision and an `ActionMenu` on a `TriangleDownIcon` `IconButton` ("More approve options"). Its one item, "<label> and go to the next one", sends the same intent with `next: true`. "Approve" (`ProposalEntry.tsx`), "Resolve conversation" (`RequestActions.tsx`), and "Accept" on the request detail (`SuggestionActions.tsx` with `detail`) use it.
  - `requestAction`: after a write with `next`, it reads Q1 `awaiting=user&sort=created&limit=2` of the review, skips the current request, and redirects to `/requests/<id>`, or to `/reviews/<reviewId>/requests?awaiting=user` when none waits. A failed write returns the error as before.
  - `requestLoader` returns `RequestDetailData`, the request with `nextRequestId` from the same Q1 read. The sticky action bar shows "Next request", a `Button` as a React Router `Link`, while it is not null.
  - `UnsavedCommentGuard` has `useConfirmDiscard()`, which shows its one dialog on demand. The split item calls it before it sends, because a redirect of a fetcher action does not pass `useBlocker`.
  - The fake Q1 honours `limit`.
  - `docs/user/requests.md`: "Next request" and the split menu.
- **Files:** `assets/requests/SplitDecisionButton.tsx` (new), `assets/requests/ProposalEntry.tsx`, `assets/requests/RequestActions.tsx`, `assets/requests/SuggestionActions.tsx`, `assets/requests/ActionBar.tsx`, `assets/requests/requestIntent.ts`, `assets/routes/requests/requestData.ts`, `assets/routes/requests/RequestDetail.tsx`, `assets/comments/UnsavedCommentGuard.tsx`, `tests/ui/NextRequest.spec.ts` (new), `tests/ui/CarryOver.spec.ts`, `tests/ui/support/fakeReview.ts`, `docs/user/requests.md`.
- **Tests:** UI `NextRequest`:
  - "Approve and go to the next one sends Q15 with the checkbox value and opens the oldest other waiting request".
  - "Resolve conversation and Accept with go to the next one send their command and open the next request".
  - "With no other request waiting, the item opens the request list with Waiting for you".
  - "A failed command keeps the page and shows the error".
  - "With an unsaved reply the item asks first: Keep editing sends nothing, and Discard sends and opens the next request".
  - "Next request links to the oldest other waiting request, and does not show when none waits".
- **Verification:**
  - `make front`: 125 tests. `make ui`: 230 passed.
  - Mutation check: without the exclusion of the current request (`page.items[0]`), the "Next request links" case fails. Without the discard confirmation, the unsaved-reply case fails.
  - `startRedirectNavigation` in `node_modules/react-router/dist/development/lib/router/router.js` does not call `shouldBlockNavigation`; only `navigate()` and a history pop do.
  - Journey `RequestStages` passes. Its screenshots show the split buttons in the action bar and on the suggestion, at 1728 px light and 390 px dark.
- **Deviations:**
  - The Verify item is "Resolve conversation and go to the next one", because the button is "Resolve conversation" (`REQUEST_BUTTON_LABELS`, user docs).
  - `UnsavedCommentGuard.tsx` is changed, and the split item asks before the write. The scope expects the guard to ask on a move to the next request, and the redirect skips the blocker. Without the change, a typed reply is lost without a question.
  - One extra UI case for that guard path.
  - "Accept" in the code view stays a plain button: the scope covers the request page only.
  - `tests/ui/CarryOver.spec.ts` answers Q1, because the request loader now reads it.
- **Follow-ups and open questions:**
  - The request loader reads Q3, then Q1, so each load and live revalidation of the request page waits for two reads in sequence. A next request field on Q3 would make it one read, as a contract change.
  - The fake Q1 serves one page without a cursor (`shortcut:` comment in `fakeReview.ts`).
  - No journey capture of the open split menu or of "Next request".
- **Risks discovered:**
  - A redirect of a fetcher action skips the unsaved-comment guard. A new action that redirects from a page with comment boxes must call `useConfirmDiscard()` first.
  - When the write succeeds and the Q1 read of the action fails, the page shows the read error. The decision is saved, and the revalidated page shows it.
