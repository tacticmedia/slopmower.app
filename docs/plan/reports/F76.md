## Report: F76 Delivery choices

- **Status:** Done 2026-10-29, `1bc1b2d`.
- **Summary:**
  - D85: `Delivery {workspace, pullRequest}`, null meaning that the agent decides. `Workspace` is the open set `current_branch`, `new_branch`, `worktree` (PHP enum, `common.schema.json`, `WORKSPACES`).
  - "Submit feedback" (D5) takes `delivery?`. `batch.submitted` stores it, `ReviewReducer` folds it into `ReviewSnapshot.delivery`, and `Review` keeps it in the new columns `delivery_workspace` and `delivery_pull_request` (migration `Version20261029100714`). Without a value the review keeps its choice.
  - Q15 takes `pullRequest?`. `request.proposal_approved` stores it, and `Proposal` holds it as a third field in the jsonb state of F89, so a release, a won't do, or a reopen clears it with the plan.
  - `RequestState::delivery()` gives the effective value: the workspace of the review, and the pull request choice of an approved proposal before that of the review. `Review` and `Request` show `delivery` and `capabilities {pullRequests}` (from `RepositorySource::hasPullRequests()`, D83). `pullRequest: true` without the capability answers 422 on `delivery.pullRequest` (D5) or `pullRequest` (Q15).
  - SPA: `SubmitFeedbackOverlay` has the selects "Branch" and "Pull request", which start from `review.delivery`; the second shows with the capability only. Approve has the checkbox "Send as a pull request" with the capability, which starts from the effective value, and sends it.
  - The skill (both copies), the MCP server instructions, and the descriptions of `get_request` and `link_pull_request` say what each value means. The user pages `comment.md` and `requests.md` describe the choices.
