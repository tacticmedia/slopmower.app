## Report: M28 Re-anchoring core

- **Summary:** `src/Domain/Anchoring` holds the pure functions of architecture section 5.4 on line arrays, without git. `UnifiedZeroDiffParser` reads the hunks of one file's `git diff --unified=0`. `RangeMapper::mapRange()` maps a `LineRange` through the hunks to a `MappedRange` with `untouched` and `keepsSomeLines()`. `SnapshotMatcher` finds exact matches in comparison form, picks the nearest, and reports a tie as an ambiguous `ExactMatch`. `LineSimilarity::between()` is the LCS formula. `BestWindow::near()` gives the best `FuzzyMatch` of 0.6 or more. - **Deviations and decisions:**
  - Deviation from the section 5.4 pseudo-code, decided by the orchestrator: `BestWindow` does not search a snapshot that is not distinctive. The pseudo-code guards only the exact search, but F10 says "No content search, diff mapping only", and a fuzzy window is a content search. Without the guard, a deleted `}` would become `changed` at the nearest other `}`. The architecture document is unchanged.
  - Decision for Jan: `BestWindow::MAX_SIMILARITY_RUNS` is 1000. The search visits windows nearest first and stops after 1000 full LCS runs with the best window so far, so the result stays deterministic and the cost stays at about 1 s for a 200-line snapshot. The price: a far and edited move in a repetitive file gives no window, so M29 returns `orphaned`.
  - `keepsSomeLines()` is true when the mapped range has at least one line. So a region whose lines are all rewritten in place gives `changed` with a similarity, and an edited one-line anchor is F5, not `orphaned`. Only a deletion of the whole region keeps no lines.
  - A boundary line inside a hunk maps to the whole new side: the start line to the first new line, the end line to the last new line. Inside a pure deletion, the start maps to the line after it and the end to the line before it, which gives an empty range. `MappedRange::$startLine` is also set for an empty range, as the reference of `nearest`.
  - `untouched` means that no hunk removes or changes a line of the region and no insertion falls between two of its lines. An insertion directly above the first line or directly below the last line leaves it untouched.
  - `BestWindow` searches the whole file, because section 5.4 defines no radius. The highest score wins, then the window nearest to the mapped start, then the upper window. A window has `lineCount` lines, or all lines of a shorter file. For a truncated snapshot, it compares the kept lines of each window, the first and last 100, with `snapshot.lines`. A multiset upper limit of the LCS skips windows that cannot win.
  - `SnapshotMatcher`: a snapshot is distinctive when its `lines` in comparison form have 8 or more characters other than spaces, counted in UTF-8 characters. An untruncated snapshot matches a window with equal comparison forms. A truncated snapshot needs equal kept lines and an equal `normalizedHash`. `nearestMatch()` returns null when the snapshot is not distinctive or has no match. `exactMatches()` returns all matches in file order, for `searchOtherFiles` in M29.
  - `LineSimilarity::between()` of two empty lists is 1.
  - `UnifiedZeroDiffParser` skips the lines before the first hunk as the file header. It throws `\UnexpectedValueException` for a context line, a second `diff` header, a `Binary files` line, or a hunk whose `-` and `+` lines contradict its header counts. A message names a line by its number, never by its content, because the content is repository code. Malformed git output is an internal error, not a `DomainError`.
  - `SnapshotCapture::keptLines()` is new and public, so that capture and the search share one truncation rule. This is the only change to M02 code.
  - Tests beyond the acceptance list: the nearest-match case, the deleted-region and insertion-boundary cases of `RangeMapper`, the parser rejections, the short file, the run budget, and the trivial snapshot of `BestWindow`. Each proves one rule of our own.

- **Risks discovered:**
  - The multiset limit prunes poorly when most lines of the file and the snapshot are the same few texts. Without the run budget, reviewers measured about 0.9 ms per full LCS run, 18.6 s for 20000 repetitive lines, and 1.28 s for a moved, edited 200-line region of `composer.lock`. With the budget, one search costs at most 1000 runs plus one pass over the windows, about 1 s for a 200-line snapshot. The cache key of M29 includes the target SHA, so each new default-branch head pays this again.
