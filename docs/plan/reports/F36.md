- **Decisions and deviations:**
  - **Clean workspace.** The scope keeps `vendor/` and `node_modules/` of the earlier run in `var/act/workspace/`. `bin/act-run` keeps nothing that git ignores, as on a GitHub checkout:
    - the rsync of macOS (openrsync 2.6.9 compatible) deletes protected (`P`) paths under `--delete-excluded`;
    - `npm ci` in the workflow removes `node_modules/` anyway;
    - the entrypoint installs `vendor/` only when it is empty, so a kept `vendor/` skips `composer install` and its scripts, which every GitHub run executes, and goes stale on a lock change;
    - the measured cost of the install inside `make up` is small: `make up` took 36 to 43 s with an empty `vendor/`.
  - **Composer cache needs `compose.yaml`.** The entrypoint downloads the packages inside the `php` container, so the workflow sets `COMPOSER_CACHE_DIR=/app/var/composer-cache`, and `compose.yaml` passes it to `php` with a key-only entry: unset when the shell does not set it (checked in the container: Composer then uses `/root/.cache/composer`). `compose.yaml` is not in the in-scope list of the scope file.
  - **`actions/upload-artifact` v5.0.0, not the latest v7.0.2.** The artifact server of act 0.2.89, the latest act release, refuses v7 (unknown field `mime_type`) and v6.0.0 ("Error unauthorized" on the signed upload URL; v6 bundles `@azure/storage-blob` 12.29.1, v5 bundles 12.17.0). A small act workflow showed v4.6.2 and v5.0.0 upload and finalize, and v6.0.0 fail, also with act in UTC. One step for GitHub and act keeps the step that `make act` verifies the step that GitHub runs. v5.0.0 declares `node20`; GitHub runs it on Node 24.
  - **Other action versions,** looked up on 2026-10-08 with `git ls-remote`, all lightweight tags: `actions/checkout` v7.0.1, `actions/setup-node` v7.0.0, `actions/cache` v6.1.0 (v1 cache API while `ACTIONS_CACHE_SERVICE_V2` is unset, which the act cache server serves), `docker/setup-buildx-action` v4.4.1, `docker/bake-action` v7.4.0.
  - **Docker layer cache.** `docker/setup-buildx-action` creates a `docker-container` builder and selects it. `docker/bake-action` builds the compose targets `php` and `symbols` from `source: .` with the GitHub Actions cache, one cache scope per target, without `load`: the build only fills the builder cache, and the build of `make up` on the selected builder reuses it. `worker` builds the same target as `php`. Both steps are skipped under act, where the host daemon has its own build cache. They are not verifiable locally.
  - **`var/` for the runner user.** A step creates `var/` before `make up`. On a Linux runner, the `php` container writes as root and Docker creates the bind-mount source `var/local-repositories` as root, and the host-side `make ui` writes `var/ui/`. Docker Desktop on macOS maps the owner, so act cannot show this.
  - **Guard step under act.** `.actrc` holds `--bind`, so a plain `act` in the checkout would bind it, and `npm ci` would replace its `node_modules/` with Linux binaries. The first step, `if: ${{ env.ACT }}`, fails the run when `GITHUB_WORKSPACE` is not `*/var/act/workspace`. It is not environment setup, but it is skipped on GitHub.
  - **One act run per Docker daemon.** act names the job container `act-QA-qa-<hash>` from the workflow and job names only, and removes an existing container with that name before it starts (`stopJobContainer`). `bin/act-run` waits while that container runs, at most an hour. So one compose project name, `holistic-review-act`, is enough, and `bin/act-run` downs only a project whose name ends in `-act`.
  - **act caches.** The action and cache servers of act keep their default directories under `~/.cache/`: their keys are content hashes, and every checkout shares the warm caches. Only the artifacts go to `var/act/artifacts/`, which `bin/act-run` empties before each run.
  - **`.actrc`:** `-P ubuntu-24.04=catthehacker/ubuntu:act-24.04`, `--bind`, `--env-file .github/act.env`, and `--rm`, which removes the job container after a failed run too. `bin/act-run` adds `--artifact-server-path` and the `ACT_*` port overrides with `--env`, which win over the env file.
  - **Stamp, changed in review.** The first version touched `var/act/verified` and compared modification times, so every new worktree, and every checkout or rebase that rewrote an `ACT_INPUTS` file, ran act again, and a second concurrent run failed `make check`. The `act` target now records `ACT_HASH`, the hash of the names and content of `ACT_INPUTS` (`git hash-object --stdin`), as a file in `ACT_VERIFIED`, `.git/act-verified/` of the git common directory. `make check` runs `make act` when that file is missing. A direct `make act` also counts. `bin/act-run` waits for the act container of another checkout instead of failing. `ACT_INPUTS` also lists `bin/act-run`.
  - **Gate condition.** The scope names `if: ${{ !cancelled() }}`. Gate steps use `if: ${{ !cancelled() && steps.up.outcome != 'skipped' }}`: they run once `make up` has run, also after a failed gate or a failed `make up`. A failed guard or setup step skips `make up`, and with it every gate. With `!cancelled()` alone, a plain `act` in this worktree ran the gates in the bound checkout after the failed guard; they failed on the macOS native binaries of `node_modules/` and wrote nothing but `var/ui/test-results/.last-run.json`. The upload of the failure files has the same `make up` condition. `make db-test` keeps the default, so after a failed `make up` it is skipped and `make e2e` fails on the missing `app_e2e`.
  - **Workflow defaults:** `permissions: contents: read`, `timeout-minutes: 60`. Cache keys: `composer-<hash of composer.lock>` with the prefix as restore key, `playwright-<os>-<arch>-<version of @playwright/test>`, and the npm cache of `actions/setup-node` on both lock files.
  - **Acceptance test 2 in one run.** All seven failures went into one act run: each gate step failed with its own message, and the other gates ran and passed. The failure of `composer.json` is an out-of-date lock file, because a schema-invalid file stops `make up` (above).
  - **Test.** `QaWorkflowTest` is the automated form of acceptance test 5, plus the rule that the workflow runs each gate of `make check`.
- **Follow-ups and new ideas:**
  - **Stale link.** `docs/plan/F36-qa-pipeline.md` links `../backlog/qa-pipeline.md`, which this feature deletes.
  - **First GitHub run.** The steps that act skips or cannot show (Buildx, the bake layer cache, the GitHub cache service v2, the artifact upload to GitHub, the root-owned `var/`) are checked only by actionlint. Jan checks the first run after the push. Branch protection on `main` stays with Jan.
  - **Stale lock and `make up`.** With an out-of-date `composer.lock`, the first `composer install` of the entrypoint fails in its `post-install-cmd` `composer normalize`, the container restarts, and the second start skips the install because `vendor/` is no longer empty. `make up --wait` fails or passes depending on timing: 1 of 4 act runs with that injection failed `make up`. Candidate: let the entrypoint fail clearly, or run `composer normalize` only on `update`.
  - **Linux hosts.** On a Linux host, the containers write root-owned files into `var/act/workspace/`, and the next `bin/act-run` cannot delete them. Docker Desktop on macOS maps the owner.
  - **Candidates:** Dependabot for the pinned action SHAs; a `concurrency` group that cancels a superseded run of the same ref; `actions/upload-artifact` v7 once act accepts it.
  - **Composer warnings.** `composer validate` warns about the unbound constraint of `ergebnis/composer-normalize` and the exact constraint of `symfony/reprise`. Warnings do not fail the gate.
