## Report: F24 Gutter "+" keeps the focus

- **Status:** Done (awaiting merge). One commit `fix: F24 gutter plus keeps the focus` on the worktree branch, based on `cd2fb7e`.
- **Summary:**
  - Cause, measured in `@pierre/diffs` 1.5.2: the scroll that the focus causes queues a render on the next animation frame. Its `InteractionManager.setup()` calls `placeUtility()`, and `showUtilityOnLine()` appends the gutter utility container to the line number element again. That moves the focused "+" in the DOM, so the focus goes to `body`. The row is not rendered again: the same button goes back into the same number element, in the same task.
  - Chrome fires `focusout` with no related target inside that `appendChild()`, before the move. At that moment the button is still connected, and in the next microtask it is connected again.
  - `keyboardGutterUtility()` in `assets/code/CodeFile.tsx` now watches the shadow root of the view with a `MutationObserver` while a "+" has the focus. When a mutation inserts the "+" of the focused line again and the focus is on `body`, it focuses that "+" with `preventScroll`. A focusout with a related target, or one after which no insertion gives the focus back, stops the observer.
- **Files:**
  - Front end: `assets/code/CodeFile.tsx` (`keyboardGutterUtility()`).
  - Tests: `tests/ui/KeyboardCommentOnLines.spec.ts`.
  - Docs: `docs/architecture.md` (section 8, "Differences from the GitHub PR UI", row "'+' works with the keyboard", Reason cell).
- **Tests added:**

    - "The gutter + outside the visible code keeps the focus that Tab gives it, and Space opens the comment box": `#L100` of the large file, the view scrolled by half its height plus 60 px, so the row of line 100 is rendered above the visible code. Tab from "Copy path" focuses the "+", the test waits two animation frames for the render, then checks the focus and presses Space. Before the fix: 20 of 20 runs fail at the focus check (`inactive`). After the fix: 20 of 20 pass.
    - "The gutter + does not take back the focus that Tab moves out of the page": the rule of this code that a focus that leaves on purpose stays away. Tab from the "+" leaves the page, a scroll of 60 px makes the view insert the "+" again, and the "+" must not have the focus. Without the release in the focusout microtask: 20 of 20 runs fail (`focused`).

- **Decisions and deviations:**
  - The scope's detection "its focusout has no related target and the button is no longer connected" does not hold in Chrome: the button is connected during the focusout and again in the next microtask, and the library inserts the same button into the same number element. The fix detects the insertion with a `MutationObserver` instead, one of the options of the scope. The observer starts on `focusin` of a "+": a first version that started it in the focusout handler got no records of the move.
  - The records of the render reach the observer callback or, through `takeRecords()`, the microtask that the focusout queues, whichever runs first. Both call the same function, so the check does not depend on that order.
  - A focus that leaves the "+" with no related target and is not given back in the same task, for example a click outside the code or Tab out of the page, stops the observer. Without that, a later render after a scroll takes the focus back from the user.
  - `focus({ preventScroll: true })`: the browser already scrolled the "+" into view, and another scroll would start another render.
  - The "+" is in the gutter column and the threads are in the code column of the shadow root, so the "+" of a line comes before every thread in the Tab order. The manual check therefore reaches the "+" from the thread with Shift+Tab.
  - F21 is not merged, so `KeyboardCommentOnLines.spec.ts` has no 1280x1000 viewport to remove.
- **Follow-ups and new ideas:**
  - The UI suite runs Chromium only, so the fix is verified in Chromium only. The observer callback gives the focus back without a focusout during the move, but no test covers a browser that fires none.
  - The "+" also loses the focus when the user scrolls the view with the wheel or the arrow keys while it has the focus. The fix gives it back while its row stays rendered. When the row leaves the rendered range, the library removes the "+", and the focus stays on `body`.
