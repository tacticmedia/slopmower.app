## Report: F62 Scroll to a line gives up early

- **Status:** Done (awaiting merge). One commit `feat: F62 scroll to a line gives up early` on the worktree branch `f62-scroll-to-a-line`, from `b441a04`.
- **Summary:**
  - The cause: while the worker pool of the page is not ready, the view has no rows, but `VirtualizedFile.getLinePosition()` still knows the lines from its layout file, for example `{ top: 59988, height: 20 }` for line 3000. So each step takes the estimate branch of `scrollToRange()`, scrolls the window to about Y 60000, which the 1093 px page clamps at Y 373, and returns `moved`. 60 such steps end the loop after about 970 ms.
  - The fix: `scrollToRange()` scrolls through `scrollWindowTo()`, which returns `moved` only when `window.scrollY` changed. A scroll that does not move the window returns `done` when the row of the first line of the range is rendered, and `waiting` before that row. Only `moved` counts toward `MAXIMUM_SCROLL_MOVES`, so while the view has no rows, only `MAXIMUM_SCROLL_WAIT_MS` limits the wait. The F61 user input stop is unchanged.
  - With the worker held for 3 s, the loop makes 2 real moves, from 0 to 373 and, after the release, from 373 to 60090, and ends with `done` 2.84 s and 3.08 s after its start. For `#L10-L200`, a range taller than the window, the loop ends with `done` in the step after the window reached Y 577, 5 ms and 57 ms after its start.
- **Proof of the cause:** a log of each step of the loop in the page, read by a probe spec after the rows came (`var/f62/`, git-ignored, probe deleted). Before the fix, 2 of 2 runs: 60 steps, all `moved`, Y 373 before and after each step except the first, page height 1093, 0 rows, the last step at 968 ms, the window left at Y 373. After the fix, 2 of 2 runs: 172 and 187 steps, 2 `moved` and the rest `waiting` before the last step `done`, the window at Y 60090.

- **Decisions and deviations:**
  - **"The scroll target changed" is read as "the window moved".** `scrollWindowTo()` compares `window.scrollY` before and after the scroll. A scroll that the end of the page stops does not count.
  - **A window at rest ends the scroll once the first row of the range is rendered.** A scroll that does not move the window leaves it at the target or at the end of the page, so the step has nothing left to do. `isBelowHeader()` is never true for a range taller than the window below the header, so without this rule the first version repeated the same scroll for 10 s, and moved the window back after any scroll that the input events of F61 do not catch, for example a drag of the scrollbar. The rule needs the row of the first line of the range, not any row: in the step right after a scroll by the estimated heights, the rows of the old position can still be in the view, and the rows of the target can still correct the position, for example in wrap mode. Without that row, the step returns `waiting`, so a page that is too short for the line, as before the first rows, or a slow render of the rows does not use up the moves.
  - **Constants unchanged.** 2 real moves reach line 3000 of the 3500-line file, so 60 are enough.
  - **The hold of the new test is a timer in the route handler.** The scope names 3 s. A slow worker is the scenario, so the delay sits in the fake worker route, and the test itself waits only for conditions.
  - **The tall range test waits for a window at rest, not for a time.** The window has not moved for 5 frames, so the loop has had a step without a move, which ends it.
  - **No Known gotchas line.** No new rule for tests came out of the change.
