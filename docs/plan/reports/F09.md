- **Decisions and deviations:**
  - Item 1: a PHP setting, not a git-ignore entry. Symfony asks apps to commit `config/reference.php` (blog "New in Symfony 7.4: Better PHP Configuration", symfony/symfony discussion 62588). The framework-bundle 8.1 recipe neither ships nor ignores the file. `PhpConfigReferenceDumpPass` runs in every debug build and has no option. `symfony/mercure-bundle` 0.5.0 is the latest tag and still reads `function_exists('mercure_publish')`. No code calls the function, because the app publishes through the hub URL (D41).
  - Item 2: the scope's option, a separate cache directory, through `APP_CACHE_DIR`, which `KernelTrait::getCacheDir()` reads. Cache pools stay in `APP_SHARE_DIR`.
  - Item 3: a change in `src/Controller`, outside the directories the orchestrator named. The profiler configuration has no path matcher, only `collect_parameter`, which also needs a route default. Symfony's docs show `?Profiler $profiler`, but 8.1 registers no autowiring alias for `Profiler`, so the argument is `#[Autowire(service: 'profiler')] ?Profiler $profiler`, null where no profiler exists.
  - Item 4: three `src` comments and the developer guide flow 4.3 cite the step numbers of section 2.2, so they follow the new numbers. A1 holds no installation text, so the enterprise rule is in R2 and in webhooks section 1. The spec states why the recompute comes first.
  - Item 5: the Mercure 1.x steps are in the plan README gotchas, not in architecture section 12. They add one fact beyond the M24 list, from the `claims` option of `symfony/mercure-bundle` 0.5.0: `aud` defaults to `public_url`, and the app publishes to the internal `MERCURE_URL`, so the hub's `resource_identifier` or `aud` must be set.
  - Review follow-ups, at the orchestrator's request: D41, the `mercure.yaml` comment, the Q3 `excerpt` rule, and the webhook Parsing row in F06's proposed words.
  - Worker restart: the transport option `get_notify_timeout` of `symfony/doctrine-messenger` caps the idle LISTEN wait of `PostgreSqlNotifyOnIdleListener`. The stop signal listener runs only between two waits, and the wait of the same loop still follows it, so a stop took up to two waits. `check_delayed_interval` applies only without that listener, and `use_notify: false` would poll every second. 2000 ms keeps the instant wake-up and costs one delayed-message query per idle wait. `dev` only.
