- **Decisions and deviations:**
  - Dev log and Mate: `LogReader` of `symfony/ai-monolog-mate-extension` globs `var/log/*.log`, sorts by modification time, and `monolog-tail` reads the newest file. Its environment filter is `str_contains($filename, $environment)`. So the dated file needs no Mate setting.
  - Dev log name: `RotatingFileHandler` writes `{filename}-{date}` with `Y-m-d`, and its cleanup deletes only files that match `dev-<date>.log`. An existing `var/log/dev.log` stays until it is deleted by hand once.
  - Purge log, message class: the failure transport uses `SigningSerializer`, which does not implement `MessageTypeAwareSerializerInterface`. Its inner serializer `messenger.transport.native_php_serializer` does, and the signature is in the headers, so the body is the `PhpSerializer` output. `RetentionHandler` gets the inner serializer with `#[Autowire(service: ...)]`. `getMessageType()` gives null for a body that it cannot read, and the record then holds `"class": null`. It never runs `__wakeup()` or `__unserialize()`, so it also works for a class that no longer exists.
  - Purge log, batches: one `DELETE` of all old messages loads every body into the 128M worker after the commit, and a failed `ConsumeRemoteEventMessage` holds the whole webhook payload and the trace of its `ErrorDetailsStamp`. A failure storm would kill the worker after the rows are gone, with no record. Above 1000 items, the prod JSON formatter also cuts the context. So each batch has at most 100 messages, its bodies go before the log call, and each batch has its own record, written after the statement commits.
  - Purge log, order: the batch is a CTE, `WITH deleted AS (DELETE ... WHERE id IN (SELECT ... ORDER BY id LIMIT :batchSize) RETURNING id, body) SELECT ... ORDER BY id`, so the oldest IDs go first and each record lists its messages in ID order.
  - Purge log, channel: a plain `LoggerInterface`, the channel `app`, as every handler of the worker. In `prod`, `main` takes every channel except `deprecation` and `mcp`, and an `error` record activates its `fingers_crossed` buffer, so the record reaches `stderr`. No Sentry Monolog handler is configured.
  - Marketplace record: the delete is in `MarketplaceAccountSql::deleteOfTenantUser()`, because only `MarketplaceAccountSql` writes `marketplace_account` (entity docblock, architecture section 3). The purge without a tenant row does not call it: that path runs after an earlier purge, which deleted the user row.
  - Marketplace record, cancellation job: the job of F42 deletes the record on the 404 of GitHub before it purges, so the delete of the purge finds nothing. `CancelledAccountPurgeTest` passes unchanged.
  - Marketplace record, race: an installation of the account that another tenant commits at the same time can lose the record. That tenant's next sign-in reads the plan again.
  - Marketplace record, user accounts: `app_user.github_user_id` is unique, so no other tenant can have the account as its user account while the user row exists. The delete checks only the installations of other tenants.

  - Deviation, sign-in page: the shared partial `templates/_legal_links.html.twig` changes `templates/security/login.html.twig`, which the scope does not name. The rendered links are the same, and `LoginRoutesTest` passes unchanged.
