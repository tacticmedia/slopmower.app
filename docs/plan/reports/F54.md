## Report: F54 Pull request state after a late permission

- **Status:** Done (awaiting merge). One commit `feat: F54 pull request state after a late permission` on the worktree branch `f54-late-permission`, from `95a8f85`.
- **Summary:**
  - `GitHubInstallationHandler::handlePermissions()` compares the accepted permissions before and after it records the delivery, under the tenant lock. After the commit, for each `active` repository of the installation, it reads the GitHub pull request numbers that the requests of the tenant link.
  - When Pull requests: read is new, it queues a `ReadPullRequestJob` for each linked number without a record or with a record without a read state.
  - When Checks: write is new, it queues the check run of each record of a linked number through `QueueCheckRun::request()`, with its flag and its 5-second `DelayStamp`, and the same reads as for Pull requests: read.
  - The consumer already queues one `GitHubInstallationPermissionsJob` per tenant of the installation, and the tenant SQL filter limits the reads to that tenant, so each tenant queues only for its own repositories and links.

- **Decisions and deviations:**
  - "Without a record" reads as "without a read state", as the Goal says ("that have no state"). `PullRequestStateHandler::handleRead()` creates the record before it checks the permission, so a pull request that was linked while the installation lacked Pull requests: read has a record whose state is `unknown`. A literal "no record" rule would queue no read for that case. The handler queues the read for a linked number without a record and for a record whose `shownState()` is `Unknown`.
  - Check runs only for linked numbers with a record, because `CheckRunJob` takes the record ID. A new Checks: write also queues the read of each linked number without a read state, as a new Pull requests: read does. That covers a link from before F40 and a read that was skipped or failed: during a suspension, without access, or after a 404. A successful read sets the head SHA, `PullRequestStateHandler::record()` then queues the check run, and `QueueCheckRun::request()` queues nothing while a check run job of the record is queued. Without an accepted Pull requests: read, the read job only creates the record.
  - The check run goes through `QueueCheckRun::request()`, the one way to queue it, so a trigger in the debounce window adds no second job, and a job that runs before the read (no head SHA yet) clears the flag, so the read queues the next one.
  - Only `active` repositories of the installation, as the push route does. The jobs skip the others anyway.
  - The jobs are queued after `GitHubRepositoriesLock::run()` returns, so outside the transaction (plan README, "Dispatch Messenger messages only outside a database transaction"). A tenant that is being deleted queues nothing. The nested dispatches get their `TenantStamp` from `TenantContextMiddleware`, as the dispatch in `RequestCommands::linkPullRequest()` does.
  - The test goes through the job, handled with a `ReceivedStamp` as the worker does, not through the webhook endpoint. `InstallationWebhookTest` already covers the routing of `new_permissions_accepted` to each tenant.
  - The candidate "Pull request state after a late permission" in `docs/plan/features.md` stays for the orchestrator, because the feature brief gives `features.md` to it.
  - Docs beyond the scope list: one sentence in D64, because AGENTS.md puts a contract decision into architecture section 11 too, and one sentence each in the two sections of `docs/user/reviewing.md` that tell the user to accept the permission.
- **Follow-ups and new ideas:**
  - The UI spec "A file loads its diff when it scrolls into view" failed once in a full run and passed in isolation. The cause is not known.
  - `installation` `unsuspend` queues nothing. A suspended installation gets no webhook events, so after an unsuspend every linked record can be stale, not only the ones whose read or check run was skipped. Candidate "Pull request state after an unsuspend".
