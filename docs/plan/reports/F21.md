## Report: F21 File view fills the window

- **Status:** Done (awaiting merge).
- **Summary:**
  - Above 768 px, while a file is open, the window does not scroll. The app header, the review header, and the tabs stay at the top. The tree column and the file column fill the height below them and scroll on their own. The code view takes the rest of the file column, and the file-level threads take at most a third of it.
  - `ReviewLayout` sets `data-file-view` on its page while a file is open, from the same `useMatch` as focus mode. The CSS selects on it, as it already selected on `data-focus-mode`. Focus mode keeps only its own rules: it hides the headers and the banner, removes the width limit and the padding of `main`, and puts 8 px padding around the code layout. The height rules are shared.
  - The code layout has a minimum height of 20rem. In a lower window the page grows and the window scrolls.
  - While the web debug toolbar of the `dev` environment is open, the page is 36 px lower, so neither the file view nor focus mode scrolls the window.

- **Decisions and deviations:**
  - A chain of growing flex items, not a fixed `height: 100vh`. The root page, `main`, the review page, and the code layout are flex items that grow to the window bottom from the minimum of the code layout. With a fixed height, the 20rem fallback overflowed the page: the window scrolled, but past the page background and without the bottom padding of `main`.
  - The code layout sets `min-height: 20rem` next to its `flex-basis` of 20rem. The automatic minimum of a flex item is its content height, the whole tree.
  - `main` gets `width: 100%` in the file view. Its auto margins stop the stretch in a flex column.
  - The layout CSS selects on the attributes that `ReviewLayout` sets, not on a class: `[data-file-view] > .layout` and `[data-focus-mode] > .layout`. `CodeLayout` and `FileRoute` no longer add the `focus` class. The rules of `FileRoute.module.css` need no attribute, because the file route renders only in the file view. `usePreference('focus')`, `useFocusMode()`, and the outlet context are unchanged.
  - Web debug toolbar: `body:has(> .sf-toolbar-opened) .page:has([data-file-view])` sets `min-height: calc(100vh - 36px)`. The open toolbar adds a `.sf-toolbar-clearer` of 36 px below `#root`, and hides it when closed. The 36 px is the clearer height in `toolbar.css.twig` of `symfony/web-profiler-bundle`. Without the rule, the file view and focus mode scroll the window by 36 px in `dev`. The toolbar configuration is unchanged.
  - No decision row: the layout rule is decided in the scope file, and it changes no architecture or contract.
  - No test for the 20rem fallback. The geometry probe above checked it.
  - The shorter code view broke three UI tests, which passed again on the layout of `main`. At 1280x720 the code view is 292 px high, not 504 px, so more steps scroll it:
    - "Two drafts submitted with a summary appear as two threads without the Pending label" and "An unsent reply stays when a comment box opens above its line" failed in every run. Their line was out of the view, so the hover of `dragFromPlus()` scrolled the view, and the view ignored the pointer for 120 ms: no "+" showed. Hovering again showed the "+", but the hover of the "+" then scrolled again and lost it. `dragFromPlus()` now centers the line number with `scrollIntoView()`, waits for two frames and until the line number receives the pointer, and then hovers. Both tests passed 5 of 5 runs alone and 3 of 3 runs in the full suite.
    - "The gutter + of a selection has a name and opens the comment box with Enter and with Space" failed in 4 of 15 runs, and in 0 of 15 on `main`. Tab passed the thread below line 4, which scrolled the view up, and then reached the "+" of line 6, which scrolled it down. The view rendered the row of the "+" again, and the focus went to `body` before Space. F24 fixed this cause: the "+" of the same line takes the focus again after the view renders its row. The test runs at 1280x720 unchanged. The plan README gotchas name the `dragFromPlus()` rule.
  - `docs/user/reviewing.md` names scrolling only in "Focus mode". The section now says that the tree and the file fill the window below the headers, that **Focus** hides the headers, and that on a narrow screen the page scrolls.
  - Rebase onto main after F23 and F24: the "Focus" buttons are `FocusToggle` of F23, so `FileRoute.tsx` no longer reads `focus`. The keyboard focus bug of the gutter "+" that F21 found is fixed by F24, so `KeyboardCommentOnLines.spec.ts` keeps its viewport and the plan README has no gotcha for it. F23 adds the key hint to the accessible name of "Focus", so `FileViewLayout.spec.ts` finds the button in the file header without `exact`, as `FocusMode.spec.ts` does.
- **Follow-ups and new ideas:**
  - At 1280x720 the review header with the tabs ends at 328 px, so the code view gets 292 px, or 256 px with the dev toolbar open. New idea: a compact review header in the file view, for example the agent prompt and the index progress in one line or behind a disclosure.
