## Report: M15 MCP server and read tools

- **Status:** Done (awaiting commit).
- **Summary:** `symfony/mcp-bundle` 0.14.1 with `mcp/sdk` 0.8.1 serves the `holistic-review` server over Streamable HTTP at `/_mcp`, in the handshake era with file sessions under `var/mcp-sessions` and in the 2026-07-28 era with `server/discover`. The stateless `mcp` firewall reuses M14's `ApiTokenHandler` and `BearerAuthenticationFailure`, so tenant context and repository scope come from the token and reset between worker requests. `app:schema:bundle` generates `src/Mcp/BundledSchemas.php`. The five read tools call the REST queries and normalizers through `McpToolRunner`, which maps every failure to an isError result. A session belongs to the token that opened it and serves one request at a time. `McpTestClient` (KernelBrowser or HttpBrowser) carries the wire tests; `McpHttpClient` points it at the e2e site, and the three REST stand-ins of M19 now use MCP.

- **Deviations and decisions:**
  - PSR-17 aliases: Flex skipped the `nyholm/psr7` recipe ("all versions of the recipe conflict with your package versions"), so only the `php-http/discovery` set in `config/packages/http_discovery.yaml` exists. Nothing to resolve.
  - `symfony/var-exporter` (8.1.6) is now a direct requirement, because `app:schema:bundle` uses `VarExporter`; it was installed before as a dependency of DependencyInjection. `opis/json-schema` 2.6.0 moved to the runtime packages of `composer.lock`, because `mcp/sdk` validates input schemas with it. It stays in `require-dev`.
  - `BundledSchemas` holds all seven output roots of mcp.md section 4, including `REQUEST_COMMAND_RESULT` and `LINK_COMMITS_RESULT` for M16, because the roots of the command are the output schemas of section 4.
  - Bundling: a definition is named by its `$defs` key, a whole-file target by the file `title`; a name that stands for two targets fails the command. The root keeps every keyword except `$schema`, `$id`, and `$defs`, because `request.schema.json` has a root `allOf` that validation needs. `--check` compares without writing; the up-to-date test runs it. The generated file passes php-cs-fixer unchanged.
  - The `#[Schema]` patterns of section 3 are `McpToolRunner::ULID` and `McpToolRunner::SHA_PREFIX`; the spec writes `self::ULID`. `FULL_SHA` comes with its first user in M16. Each tool has a `NAME` constant for the attribute and the failure log.
  - `list_reviews` is R1 with `name` (`RepositoryQuery::list($repository, null, 1, null)`), then V2; no match gives `not_found`. A whitespace-only `repository` is not `invalid_input`: `LocalDirectory` allows spaces, so it resolves as R1 does and gives `not_found`.
  - Semantic checks: `list_requests` builds the REST `RequestListQuery` and validates it with the Validator, so `path` keeps the REST rules (no leading `/`, no NUL) and a violation gives isError `invalid_input` with its field. The other read tools have no rule beyond their input schema.
  - Check order: `list_requests` and `get_updates` resolve the review with `ReviewRepository::findFresh()` first, so an invisible review gives `not_found` before a cursor or path `invalid_input`, as `#[MapEntity]` does for REST.
  - `get_request` takes `at` and `context` and ignores them, as Q3 does now; `location` and `excerpt` are null.
  - The Error JSON of a `ToolCallException` is encoded with `JSON_UNESCAPED_SLASHES | JSON_UNESCAPED_UNICODE`; its `details` go through the same normalizer as REST. An unexpected failure is logged at `error` as "The MCP tool {tool} failed." with the exception, and the agent gets "An unexpected error occurred.".
  - The `mcp` firewall is stateless, so a session cookie authenticates nothing there. `access_control` requires `ROLE_AGENT` on `^/_mcp`; a call without a token reaches the entry point and gets the plain challenge.
  - `/.well-known/oauth-protected-resource` has no route; the router answers 404 before any firewall.
  - One request per MCP session at a time (orchestrator review): SDK 0.8.1 queues each response in the session and rewrites the whole session file without a lock, and FrankenPHP runs parallel workers, so two requests of one session could lose or swap a response. `SessionLockedMcpController` decorates `mcp.server.holistic_review.controller` and holds the `LockFactory` lock `mcp-session-<session ID>` around `handle()`, after the firewall. It polls for at most 30 seconds, as `FetchRepository` does, then answers 503 with `Retry-After: 1`. A request without a valid session header takes no lock. No tool suspends, so the SDK answers with JSON and never streams a response that outlives `handle()`.
  - Sessions are bound to their token (orchestrator review): `TokenBoundSessionStore` decorates `mcp.server.holistic_review.session.store` and stores each session under `Uuid::v5(<token ID>, <session ID>)`. A session ID from another token, of the same user too, answers the SDK's 404 "Session not found or has expired.", and its DELETE removes nothing. The session file is named by that UUID.
  - `McpTestClient` takes a `KernelBrowser` or an `HttpBrowser`, initializes a session on the first request, reads JSON and SSE bodies, and keeps the raw JSON of the last message, so empty objects survive schema validation. `McpHttpClient::connect($secret)` builds it with an `HttpBrowser` on `PANTHER_EXTERNAL_BASE_URI`, as the orchestrator asked for M19 and M22.
  - `tests/Fixtures/mcp/tools-list.json` holds name, title, description, input schema, and annotations of the five read tools, extracted verbatim from mcp.md section 4 by a one-off script. The SDK output matched it on the first run, key order included.
  - `EventLogQuery` stays public: M15 does not consume it.
  - Tests beyond the acceptance list, each for a rule of ours: the semantic `invalid_input`, the cross-tenant result of `list_repositories`, `list_reviews` by the other tenant's name, and the worker reset between MCP calls.

- **Risks discovered:**
  - The SDK accepts any session ID that exists in its store; `TokenBoundSessionStore` keeps a session ID valid only for the token that opened it. The binding and the session lock depend on the service IDs `mcp.server.holistic_review.controller` and `mcp.server.holistic_review.session.store`, which the bundle derives from the server name. A bundle upgrade that renames them fails the container build.
  - `initialize` and `server/discover` advertise prompts, resources, logging, and completions, which the server does not have (SDK problem 8 of the stack findings).
  - In classic mode (the e2e site) the bundle builds the server on every request and logs one "Registered manual tool" line per tool.
