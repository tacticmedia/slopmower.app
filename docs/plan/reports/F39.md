## Report: F39 Usage limits

- **Status:** Done (awaiting merge).
- **Summary:**
  - Per-tenant usage limits with the values of the free plan: connected repositories (R3), open reviews (V1), requests per review (Q2, the `new_request` drafts of D5, and the carried requests of V15), and the clone size per repository and per tenant. A call past a limit gets 409 `limit_exceeded` with `{limit, max, current}`. A value of 0 or an empty value switches a limit off.
  - The clone size is measured after each clone and fetch, and for a GitHub repository also before the clone from the `size` of the GitHub API. A clone above a size limit fails and is deleted. A fetch that passes a limit keeps the clone and fails, as does each later fetch, so a synchronous trigger gets `repository_unavailable` with `fetch_failed`.
  - Rate limits with `symfony/rate-limiter` 8.1.6: the token buckets `api_token`, `api_user`, `mcp_http`, `sync_fetch`, and `review_start`, with their state in PostgreSQL and the advisory-lock `LockFactory`. REST gets 429 `rate_limited` with `Retry-After`, `X-RateLimit-Limit`, and `X-RateLimit-Remaining`. An MCP tool call gets an `isError` result, and an MCP HTTP request past `mcp_http` gets HTTP 429 before JSON-RPC.
  - `Me.usage` lists the use and the limit of each item, and Settings shows them in the table "Usage".

- **Decisions and deviations:**
  - Fifth limiter `mcp_http`: the specification asks for a higher limit on the `^/_mcp` listener than in the tool runner. A named limiter has one configuration, so the listener uses its own limiter, keyed by token, 600 per minute. The tool runner consumes `api_token` and `api_user` per `tools/call`.
  - Clone size is `size` plus `size-pack` of `git count-objects -v`, not `size-pack` alone: git keeps the objects of a fetch of fewer than 100 objects loose (`fetch.unpackLimit`), so `size-pack` was 0 for such clones.
  - `lock_factory: null` in `rate_limiter.yaml`, and `Kernel::process()` sets `Symfony\Component\Lock\LockFactory` as the third argument of each limiter: `framework.rate_limiter` throws "requires the Lock component to be configured" for an explicit lock factory while `framework.lock` is off.
  - The pool `rate_limiter.cache` uses `cache.adapter.doctrine_dbal` with `provider: doctrine.dbal.default_connection`. The DoctrineBundle schema listener puts its table `cache_items` into the migration diff, and `ResetDatabase` truncates it.
  - Mock clock: the rate limiter policies read `microtime()` directly. `tests/Support/Clock/rate-limiter-time.php` declares `microtime()` in `Symfony\Component\RateLimiter\Policy` on top of `Clock::get()`, and `tests/bootstrap.php` loads it before any limiter runs. `ClockSensitiveTrait::mockTime()` then drives the limiters. No `symfony/phpunit-bridge` dependency.
  - The intervals of the rate limits are fixed in the configuration, and their variables set the amounts.
  - Every limiter is a token bucket, `api_user` and `review_start` too, which the specification gave as sliding windows: the `Retry-After` of a sliding window is shorter than the real wait (20 s reported for 60 s), so an agent that follows the skill is refused again. The scope file records the decision.
  - Sizes in `details` and `usage` are bytes. The size limits are set in MiB.
  - `Me.usage`: `current` of `requests_per_review` is the largest open review, and of `repository_size` the largest clone. A scoped token gets the use of the whole tenant: these are counts, not IDs, and `UsageSql` counts with raw SQL, so check and display agree.
  - Check placement: open reviews and requests per review (Q2, D5, V15) are counted inside the event transaction under the tenant row lock `FOR UPDATE`. Every connect, local and GitHub, counts and inserts inside `GitHubRepositoriesLock::run()`, whose advisory lock `github-repositories:<tenantId>` serializes the connects of a tenant, so concurrent writes cannot pass a limit. The local connect lost its lock `connect-local:<tenantId>:<directory>`, and a tenant that is being deleted now gets 404 there, as on the GitHub path.
  - Check order: 429 `rate_limited` of the per-call limiters comes right after 401, because the listener runs after the firewall. `limit_exceeded` comes last, so V1 refuses an open review only after its fetch. `review_start` and `sync_fetch` answer at the step that they protect.
  - The GitHub size read before a clone uses `GET /repos/{owner}/{repo}` with the installation token of the clone. A failed read logs a warning and skips the pre-check, because the check after the clone still applies. The clone now makes two GitHub requests, and `InstallationTokenTest` expects 2. The mock answers 404 for an unknown repository.
  - `Retry-After` is at least 1 second, because the limiter rounds the retry time down to the second. A token bucket adds its whole `amount` once per interval, so with 300 per minute the retry time after an empty bucket is 60 seconds.
  - No MCP tool writes what a usage limit counts, so criterion 1 has no MCP case, and `mcp.md` section 5 says `limit_exceeded` never arrives over MCP.
  - The writers of `GaplessSequenceTest` start 50 reviews in one tenant, so `tests/Support/bin/append-events.php` switches off the open review limit. `MeEndpointTest` leaves `usage` to `UsageTest`.
  - `docs/requirements.md`: the non-goal row "Usage limits and rate limiting" is gone, and FR1 states the limits.
  - `docs/backlog/usage-limits.md` says "done in F39", lists V15 at the requests per review, and has token buckets. `docs/backlog/README.md` says "Done in F39".
  - Existing clones have no size until their next clone or fetch, and count as 0 bytes until then. `docs/deployment.md` says so.
- **Follow-ups and new ideas:**
  - The MCP server instructions (mcp.md section 2) could name `rate_limited`. Today the skill and the error message tell the agent to wait.
  - Expired limiter rows stay in `cache_items` until their key is used again. `cache:pool:prune` on a schedule would remove them.
  - Accepted responses could carry `X-RateLimit-*` headers, so a client can slow down before a refusal.
