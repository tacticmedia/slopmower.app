## Report: F30 Sign in after sign-out

- **Status:** Done 2026-10-08. Replaced by [F34](F34.md): `ResetCsrfStrategyListener` and its `LogoutTest` case are deleted, and every Twig form sends a double-submit token.
- **Summary:**
  - The refusal inside one session is the deliberate downgrade check of `SameOriginCsrfTokenManager`. The defect of the app is that one session uses two proofs: double-submit from the React client, and only the origin from the Twig sign-in form. F34 fixes that. Only the carry-over into the new session at logout is a Symfony defect.
  - Cause, as the scope states: `SameOriginCsrfTokenManager::isTokenValid()` puts the CSRF strategies of the old session and of the logout request into the request attribute `csrf-token`. Logout starts a new session, and `SameOriginCsrfListener` writes that attribute into it on the response. The dev sign-in form sends only origin information, so the new session refuses it: "double-submit info was used in a previous request but is now missing".
  - `ResetCsrfStrategyListener`, a `LogoutEvent` listener on the `main` firewall, sets the attribute to 0. `SameOriginCsrfListener` then writes 0, which records no strategy, and still clears the double-submit cookies, because the attribute exists.
- **Files:**
  - Source: `src/Security/ResetCsrfStrategyListener.php` (new).
  - Tests: `tests/Functional/Security/LogoutTest.php`.
  - Docs: `docs/developer-guide.md` (`App\Security` count), `docs/plan/features.md` (F30 row, the Symfony upstream report under "For Jan").
- **Tests added:**
  - Functional `LogoutTest`: "After a double-submit sign-out, a same-origin form in the new session passes the CSRF check". The client signs out with a double-submit token, as the React app does, then posts a second sign-out with `Sec-Fetch-Site: same-origin` only. Before the fix the second request gets 403 "Invalid CSRF token." at line 45, after the first sign-out passed. After the fix both redirect to `/login`.
- **Verification:**
  - `make check`: exit 0, 3m31s.
    - `make cs`: 0 of 739 files to fix.
    - `make stan`: level 8, no errors.
    - `make lint`: container, YAML, Twig, mapping correct, schema in sync.
    - `make test`: OK, 1728 tests, 17021 assertions.
    - `make front`: Vitest 24 files, 60 tests.
    - `make ui`: 120 passed.
    - `make e2e`: OK, 9 tests, 240 assertions.
  - `debug:event-dispatcher LogoutEvent --dispatcher=security.event_dispatcher.main`: the listener runs after `DefaultLogoutListener`, beside `SessionLogoutListener` and `CsrfTokenClearingLogoutListener`.
  - Manual check in the dev app (Chrome, a new isolated context): "Sign in as jan", "Sign out", "Sign in as jan" again ends on `/`, and `/api/v1/me` answers 200 with `jan`. Before the fix the second sign-in showed "Invalid CSRF token."
- **Decisions and deviations:**
  - The acceptance test is functional, not E2E as the scope says. The `e2e` site has no CSRF-checked sign-in form: the local sign-in route exists only in `dev`, and "Sign in with GitHub" is a link. An E2E case would pass before the fix. The functional case uses a second sign-out as the same-origin form, because it meets the same check in the same session.
  - The listener sets the attribute to 0 instead of removing it. Without the attribute, `SameOriginCsrfListener` would also skip clearing the double-submit cookies of the logout request.
  - The attribute name is the default `framework.csrf_protection.cookie_name`, as a constant. The app does not set that option. If it ever does, `LogoutTest` fails, because its requests use the default name.
- **Follow-ups:** the Symfony upstream report under "For Jan" in `features.md`.
