## Report: F44 Retention jobs

- **Status:** Done (awaiting merge).
- **Summary:**
  - `symfony/scheduler` 8.1.8 with one schedule of the application, `App\Schedule` (the file of the Flex recipe), consumed by the existing worker as the transport `scheduler_default`. The compose `worker` command and `docs/deployment.md` name both transports.
  - Two daily jobs at 03:00 UTC, handled by `RetentionHandler`: `PruneRateLimiterCacheJob` calls `prune()` of the pool `rate_limiter.cache`, which deletes its expired rows. `PurgeFailedMessagesJob` deletes the messages of the queue `failed` whose `created_at` is older than 30 days, through `FailedMessageSql`.
  - `framework.cache.prefix_seed` is `slopmower/%kernel.environment%`, so the namespace of `rate_limiter.cache` is the same for every release directory and host, and the prune reaches every row.
  - In `prod`, no handler takes the channel `mcp`: it is out of `main` and `console`, and it has no handler of its own.
  - Retention to state in F43: rate limit rows at most one day after they expire, failed GitHub event messages 30 days, webhook delivery IDs 7 days.

- **Decisions and deviations:**
  - The schedule is `src/Schedule.php` of the Flex recipe, made `final`, with the recipe's `stateful()` checkpoint in `cache.app` and `processOnlyLastMissedRun(true)`. After a missed run, a worker that starts at or after 03:00 UTC runs it once. A worker that starts before 03:00 UTC waits for 03:00.
  - Daily at a fixed time, `RecurringMessage::every('1 day', ..., from: 03:00 UTC)`. A period without `from` starts at the first start of the worker and keeps that start only in the checkpoint. A deployment that loses the checkpoint restarts the period, so with deployments more often than once a day the jobs would never run. A cron expression would need `dragonmantank/cron-expression`.
  - The worker reads `scheduler_default` only when `async` is empty, so a backlog in `async` makes the daily run late, not lost.
  - A failed job is not retried: `scheduler_default` is not a configured transport, so it has no retry strategy and no failure transport. Messenger logs the failure at `critical`, and the job runs again the next day.
  - No lock on the schedule. Both jobs are idempotent, and the only lock store is the advisory-lock store on the ORM session (D63), which a lock held for the life of the worker would tie up. Several workers can consume the schedule.
  - Failed messages: raw SQL in `App\Messenger\FailedMessageSql`, one `DELETE` by `queue_name` and `created_at`. Messenger has no API that deletes by age: `ListableReceiverInterface::all()` and `reject()` work one message at a time and decode each body, and its envelopes do not carry `created_at`. `messenger_messages` is not a tenant table.
  - The age is `created_at`: the time the message entered the queue `failed`. A message that `messenger:failed:retry` sends back and that fails again enters with a new `created_at`. The transport writes it as UTC wall time, so the cutoff is converted to UTC.
  - The job messages have no `#[AsMessage]` routing: the worker that receives them from `scheduler_default` handles them. Both classes are in `app.tenantless_messages`, because the worker dispatches them with a `ReceivedStamp` and no `TenantStamp` through `TenantContextMiddleware`.
  - Deviation, `prefix_seed`: the scope does not name it. The default seed `_%kernel.project_dir%.%kernel.container_class%` gives `rate_limiter.cache` a new namespace for each release directory, and `DoctrineDbalAdapter::prune()` deletes only rows of the current namespace. Rows of earlier releases would stay for ever, which makes the F43 retention statement false, and hosts with other project directories would not share the limiter state of F39. The seed also fixes the namespaces of `cache.app` and `rds_credentials.cache`, so the first deployment with it starts with cold pools.
  - Logs, as the scope decides for an SDK that puts the body into its error records: in `prod`, the channel `mcp` is not logged. mcp/sdk 0.8.1 logs the full JSON-RPC body at `info` ("Received message to process.") and the tool arguments at `debug`, and also at `error`: `SchemaValidator` logs `'data' => json_encode($dataToValidate)` when the validation fails internally, `CallToolHandler` passes the `tools/call` arguments to it, and the binding errors of `ReferenceHandler` hold the argument value in their message.
  - What is lost: only the errors of the SDK itself, for example an unknown tool, a binding error outside `McpTools::run()`, a JSON encoding error, or a session error. `McpTools::run()` catches every `Throwable` of a tool call and logs it on the channel `app` at `error` (src/Mcp/McpTools.php:480), so a failed tool stays in the log. An SDK error no longer flushes the `main` buffer, so the records before it are not written either. `monolog.formatter.json` writes no stack trace (`includeStacktraces` is `false`), so an exception record holds its class, message, code, and the file and line of the throw.
  - The channel `mcp` is also out of the `prod` handler `console`. The scope named only `main`.
  - `ProdLogChannelsTest` builds the `prod` container as `debug:config` does, with the removing passes off, and reads the handlers of the loggers `monolog.logger` and `monolog.logger.mcp`. A test kernel of `prod` has no test container, and the loggers are private.
  - The namespace test calls the private `CachePoolPass::getNamespace()` through reflection with the seed `slopmower/test` and compares the result with the `item_id` of a stored row.
  - Test data: `DoctrineDbalAdapter` stamps a row with `time()`, and the Doctrine transport writes `created_at` from the system time, so the tests age the rows with SQL. The failed messages go through `messenger.transport.failed`, which proves the queue name. The `async` row is inserted with SQL, because `test` routes `async` to `in-memory://`.
  - The size line of the developer guide was out of date in all its numbers, so each one now has the measured value, not only the file count of `src/`.
- **Follow-ups and new ideas:**
  - PostgreSQL puts the failing row into the error of a NOT NULL or check violation ("DETAIL: Failing row contains (...)"), and DBAL keeps it in the exception message, which the channel `app` logs at `error`. Checked with `dbal:run-sql` on `messenger_messages`. This is the candidate "Row values in database errors" in features.md, which architecture section 12 links.
  - The jobs log nothing. A count of the deleted failed messages at `info` would reach the `prod` log only with an error in the same run.
