## Report: F13 Agent proposals

- **Status:** Done (awaiting merge). One commit `feat: F13 agent proposals` on the worktree branch, based on `7293093`.
- **Summary:**
  - A request can ask for a plan first: `requireApproval`, set by Q2, D2, D3 (new-request drafts), D5, and V15 from its source, and fixed after the request opens. `request.opened` carries it, and a stored payload without it reads `false`.
  - The claiming agent proposes with Q14 or the MCP tool `propose_solution`: a Markdown plan and an optional unified diff (`ProposedDiff`: git format, 1 to 65,536 characters, 1 to 9 `diff --git ` lines), stored in the `request.proposed` payload. The user approves with Q15 or requests changes with Q16 and a note. Both name `proposalEventId`; another ID than the pending proposal gives 422.
  - `proposal: {eventId, state} | null` is a sub-state of the claim. `AllowedActions` opens `link_commits` and `mark_ready_for_review` only through `$proposalGateOpen`. `awaiting` rule 2 counts a decision as a user message, and rule 3 matches a pending proposal. Release, won't do, and reopen clear the proposal.
  - UI: "Ask for a plan first", checked by default, in every new-request box and in the edit of a new-request draft. The request detail shows "Plan required", and each proposal shows its plan, a `FileDiff` per file through `ProposalDiff` in `CommitDiff.tsx`, "Download .diff", "Approve" and "Request changes", or its state. The request list shows "Plan to approve".
  - The skill, the MCP server instructions, and decision D49 describe the flow.

- **Decisions and deviations:**
  - D2 refuses `requireApproval` on a reply draft with 422 too, as D3 does, so the two draft writes agree. The scope names only D3.
  - The claiming agent may always propose while it holds a request, so its `allowedActions` in progress gain `propose_solution`. The agent-view fixtures (`request.in-progress`, `request.with-excerpt`, `request-command-result.claim`, `request-command-result.question`) and the wire example of `mcp.md` section 7 list it.
  - The approve note is optional and unchecked, like the verify note. The reject note follows the required-note rule.
  - `RequestReducer` throws a `LogicException` for a decision that does not name the pending proposal, as it does for a commit event of an unlinked commit. The decider rules make it unreachable.
  - `ProposedDiff` counts the lines that start with `diff --git `; the text does not have to start with one. The length is in code points, as `Assert\Length` counts.
  - `EventNormalizer` writes the diff as its string, as it writes `WontDoReason`, so `ValueObjectNormalizer` keeps its list.
  - The bool reader with a default is `PayloadReader::boolOr()`: a missing key gives the default, a present key must be a boolean.
  - Fixtures: the new request of the proposal fixtures is `01K6B3P2A9QRSTVWXYZ012345A`, because `...0123459` is taken by `carry-over-result.mixed.json`. `request.proposal-pending.json` is the user's view, which the UI shows. The draft fixtures keep `requireApproval: false`, the story of the other fixtures; the stored `request.opened-general` event has `true`, so the round trip covers both values.
  - Schemas: `requireApproval` of the inputs is `boolean|null`, as optional properties may be sent as null. `Draft.requireApproval` follows `body`, and a reply has `const: false`.
  - D3 runs the edit before the closed-review check, so `invalid_input` comes before `review_closed`, as README section 4 orders them.
  - UI: the decision buttons show only on the request detail. The code-view thread shows the plan, the state label, and the link "Open the proposal". A pending proposal that the caller cannot decide, for example on a closed review, shows "Waiting for approval". `useRequestCommand()` holds the command state of the request detail, which `RequestActions` and the proposal decision share: the fetcher, the transition, the open dialog, the error, and a ref guard against a quick second click, as `useSubmitOnce` has. `RequestActions` gains that guard. A failed new-request write keeps the checkbox state.
  - Test support: the 4 proposal states of `RequestScenario` are in progress. "plan required" with a link is reached through propose, approve, link, ready, reopen, and a second claim, because a link needs the gate open.
  - `VerticalSliceTest` unchecks "Ask for a plan first", because the default makes its request require approval. Nine existing UI specs expect `requireApproval: true` in the Q2, D2, and D3 bodies.
  - The developer guide counts are the current file counts, which also corrects counts that earlier features left behind.
- **Follow-ups and new ideas:**
  - The manual check with Claude Code and the re-installed skill is for Jan. Re-install the skill after the merge, because an old copy calls `link_commits` and gets `invalid_transition`.
  - A pending proposal does not show in the code view header of the file, only in its thread. A label in the file tree or the file header is a candidate.
  - The `invalid_transition` message of a closed gate says only "The request is in_progress, so link_commits is not allowed." A message that names the proposal state would help an agent with an old skill.
  - A proposed diff that starts after line 1 shows the library's "N unmodified lines" separator, which cannot expand, because the patch holds no file content.
  - "Withdrawn" also labels an approved proposal whose request was reopened, by the rule of the scope. A label "Done" for an approved proposal of a request that reached `ready_for_review` could read better.
