- **Deviations and decisions:**
  - `MarkReadyForReview` runs the command first. Only `commits_not_available` gives the synchronous fetch, then the command runs again and reads the links again. The decider checks pending links last, so `invalid_input`, `review_closed`, and `invalid_transition` come before any fetch. A command with pending links takes the tenant lock twice.
  - `LinkCommitsResult.requests` holds every named request in input order, also when no event is written (the schema has `minItems: 1`). `state` is `available` when the clone has the commit at link time, else `pending`.
  - `LinkCommits` reads the clone through `TenantDataPaths::clonePath()`, not `cloneReady()`, because Q7 has no `repository_unavailable`: a missing clone counts as a missing commit. It requests the fetch whenever the commit is missing, also when every pair was linked already. A removed repository makes `FetchRepository::request()` throw `removed`; `LinkCommits` ignores it, the link stays pending, and Q10 answers `repository_unavailable`. A repository whose clone failed gets its clone queued again, as R5 does.
  - `FetchRepository::request()` takes `$delayMilliseconds` and adds a `DelayStamp` (M09 follow-up). The 5 s are `LinkCommits::FETCH_DELAY_MILLISECONDS`.
  - `ResolvePendingCommitLinks` writes `commit.found` for closed reviews too: section 2.2 names every pending link of the repository, and it is a system event, not an agent write. Each transaction reads the pending links again under the tenant lock, so a fetch of the worker and one of Q10 cannot write two events for the same links.
  - `UnlinkCommit` deletes the pin after the transaction. A git failure there (a removed repository has no clone) is logged as a warning, and the unlink stays. `update-ref -d` of a missing pin succeeds, so a pending link unlinks without a warning (checked once with the profiler logs).
  - `GitReader::commitInfo()` reads `%ct` and `%s` with `git log -1`; invalid UTF-8 in the subject is replaced (`mb_scrub()`), because event payloads are JSON.
  - Bearer-only: `#[IsGranted(AgentUser::ROLE, message: CurrentActor::BEARER_ONLY)]` on the class `AgentRequestController` and on Q7. `#[MapEntity]` resolves first (404), `IsGranted` runs at priority 20 and the payload validation at -10100 of `kernel.controller_arguments`, so a session gets 403 before 422. Route names: `api_request_claim`, `api_request_unlink_commit`, `api_request_ready`, `api_commit_link_create`. A malformed SHA in the Q8 path is 422 on `commitSha`.
  - Semantic checks of the tools come from the decider (whitespace body or note, reason after trimming, IDs that repeat in another case), not from `McpToolRunner::validate()` with the REST DTOs (M15 follow-up). Fields equal REST; messages can differ from the REST validator messages.
  - Q7 body: `LinkCommitsInput::$requestIds` has `#[Assert\Unique(normalizer: 'strtoupper')]`, so a repeated ID gives 422 on `requestIds` before the 404 of an unknown ID (orchestrator review).
  - The deprecation of the named autowiring alias `$githubClient` is gone: `InstallationTokenProvider` and `InstallationSync` inject `#[Target('github.client')]` (orchestrator review; `debug:container --deprecations` is empty).
  - Cross-tenant inventories: `CrossTenantCases` takes body placeholders and a `bearer` flag; the four bearer-only routes run with a token of the caller's tenant, because a session gets 403 on Q7 before the 404 of a body ID. `McpCrossTenantCases` takes lists and booleans.
  - `McpRestParityTest` runs each tool on one request and its endpoint on a twin in the same state at a frozen clock, and compares the bodies with the twin's ID mapped and `seq`, `eventId`, `commentId`, and `lastEventSeq` masked.
  - `phpunit.dist.xml` sets `memory_limit` to 512M: the unit and functional suites peaked at 131 MB, above the 128M default of the php container (baseline 107 MB).
  - Test seams: the in-memory transport honours `DelayStamp`, so `PendingLinkResolutionTest` moves the mock clock 6 s forward before it runs the queue, and `LinkCommitsTest` reads `getSent()`. `AgentApiFixtures::countFetches()` adds a `RepositoryFetched` listener and calls `disableReboot()`, as `StartReviewPinRollbackTest` does.

- **Risks discovered:**
  - Pins are written without the repository lock, by design. An unlink that deletes the last pin while a link of the same commit in another request has pinned but not committed yet leaves that link `available` without a pin until a later unlink and link.
  - A pending link stays pending when its commit arrives in the clone outside a fetch, for example when another request links the same commit as `available`; the next fetch resolves it.
  - The worker crash of M11 and M13 happened again: recreating `php` rebuilt the shared `dev` container, the worker died on a missing container file, and its clone message stayed delivered. Setting `delivered_at` to null released it.
  - The peak memory of the suites grows with the test count. 512M leaves room; the cause of the growth is not measured.
