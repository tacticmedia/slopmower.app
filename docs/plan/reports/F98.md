## Report: F98 Comment groups

- **Status:** Done 2026-11-03.
- **Summary:**
  - D103: a request has an optional `group`, `$defs/Group` of `common.schema.json`: 1 to 80 characters after trimming, one line without CR or LF, or null. `Request`, `RequestSummary`, and `Draft` have the required property `group`. Q2, D2, and D3 take the optional input `group`; the compound constraint `RequestGroup` checks it as `RequestTitle` checks a title, so a blank group or one with a line break answers 422 on `group`.
  - `Draft.group` is the column `group_label` (`VARCHAR(80) DEFAULT NULL`, migration `Version20261103020738`), because `group` is an SQL keyword. The draft stores it trimmed. `Draft::edit()` replaces it as it replaces `title`, so an absent or null group removes it, and refuses a group on a reply with 422 on `group`. `CreateDraftInput` refuses a group on a reply with `When` and `IsNull`.
  - `Open`, `RequestOpenedEvent`, and `RequestState` carry `group` with the default null. `RequestDecider` trims it from `Open` into the event, and `RequestReducer` copies it into the state. The payload of `request.opened` and `change_request.state` both read a missing `group` as null, so stored events and rows need no change and no rebuild. No event changes the group, and a suggestion has none.
  - D5 (`decideDraft`) passes the draft group, Q2 the input group, and V15 (`CarryOverController`) copies the group of the source.
  - Q1 and `list_requests` take the filter `group`: `JSONB_PATH_TEXT(request.state, 'group') = :group` in `RequestQuery::filter()`, an exact match. `RequestListQuery` checks UTF-8 and at most 80 characters, and an empty value is no filter. The filter is part of the cursor filters.
  - Agent rule: a new step 7 in the MCP server instructions (`config/services.yaml` and `docs/specs/mcp.md` section 2, steps 7 to 9 became 8 to 10), the `list_requests` and `get_request` descriptions in `mcp-tools.json`, and a bullet under step 1 of section 4 in the skill: requests with the same `group` are one unit; read them with `list_requests` and `group`, claim each, make one change in one commit linked to every request, mark each ready with the same note, and with `requireApproval` propose the same plan on each.
  - SPA: `CommentBox` shows a "Group" `TextInput` next to the "Type" select wherever the select shows. Its native `datalist` holds the sorted, unique group labels of the caller's drafts, read from the `review` route loader, which the D2 and D3 fetchers revalidate. `CommentText` has `group`, absent when blank, so D2 and D3 bodies carry it only when set. `DraftBox` shows a `Label` "Group: <label>" and edits the group. `GroupLink` links a group to `/reviews/<id>/requests?group=<label>`: in the meta line of `RequestRow` and in a "Group" section of `RequestSidebar`. The request list sends `group` to Q1, and the list header shows the filter as a button "Group: <label>" that removes it. The file composer keeps the group when a D2 fails.
  - The fake Q1, Q2, D2, D3, and D5 of the UI suite filter, store, and pass the group, and the fake D3 refuses a group on a reply.
  - F97 follow-up: a draft edit (`initialTextSaved`) counts as unsaved when its type or its group differs from the initial value, not only its title or body.

- **Deviations:**
  - The F97 follow-up "a change of only the type in the draft editor does not count as unsaved" is fixed here, for the type and the group, on the decision of the orchestrator. It has the UI case in `UnsavedComment`.
  - The acceptance test "a suggestion of the datalist fills the field" checks the options of the `datalist` that the field names in `list`: Playwright cannot open the native suggestion list of headless Chromium (`ArrowDown` and `Enter` leave the typed text). That a chosen option fills the field is browser behaviour.
  - The request list header shows an active group filter as a button "Group: <label>" that removes it. The scope file names only the link; without the button the filter is invisible and can only be removed through the address.
  - The column of `Draft.group` is `group_label`, because `group` is an SQL keyword.
  - The case for Q2 with `group` is part of the Q1 and `list_requests` case. `CarryOverController` copies the group, but no test covers the copy, because the acceptance tests list none.
- **Follow-ups and open questions:**
  - No test covers the V15 copy of the group or the "Group" section of the request detail sidebar.
  - The datalist offers the groups of pending drafts only. A group of submitted requests is not suggested (out of scope), so a draft written after a submit can start a second group with a typo.
  - A group spans one review. Two reviews can use the same label for unrelated work, and V15 carries a label into the target review, where it can join an existing group of that label.
  - No journey shows a request row or the sidebar with a group, or the group filter button.
