## Report: F40 Pull request state

- **Status:** Done (awaiting merge). One commit `feat: F40 pull request state` on the worktree branch `f40-pull-request-state`, based on `6172503`.
- **Summary:**
  - `Request.pullRequests` (REST Q3 and MCP `get_request`): one `{url, state, title}` per URL of `pullRequestUrls`. `state` is the closed set `PullRequestState`: `open`, `draft`, `merged`, `closed`, or `unknown`, with `title` null for `unknown`.
  - A tenant-owned `pull_request` record per repository and number holds title, state, merged, draft, head SHA, head repository, and GitHub `updated_at`. A new link of a GitHub pull request queues `ReadPullRequestJob`: it creates the record, and reads `GET /repos/{owner}/{repo}/pulls/{number}` with a token that asks for `pull_requests: read`, unless the installation lacks the permission, is suspended, or the repository lost its access.
  - The `pull_request` webhook updates the record of each tenant that has one, from the payload, without an API call. An older `updated_at` changes nothing. A changed state or title publishes the live update `pull_request {reviewId, requestIds}` per review.
  - `GitHubInstallation.permissions` (jsonb) comes from the sign-in listing and the `installation` events `created` and `new_permissions_accepted`. `InstallationTokenProvider::forRepository()` takes the permissions of its job.
  - For a GitHub repository, `link_pull_request` and `unlink_pull_request` match a linked pull request by its number, so a link under an earlier name of the repository still matches after a rename.
  - UI: a Primer `StateLabel` next to each linked pull request in the request header, with the title, and in the thread entry. The `pull_request` live update revalidates the open review.

- **Decisions and deviations:**
  - Test classes: the scope names `InstallationTokenProviderTest` and `GitHubWebhookTest`. The token case extends the existing `InstallationTokenTest`, the `new_permissions_accepted` case goes into the existing `InstallationWebhookTest`, and the three `pull_request` cases into a new `PullRequestWebhookTest`, as the webhook tests are split per event.
  - The reducer keeps its exact URL match. The decider matches by number and writes `pull_request.unlinked` with the URL as linked, so a projection rebuild stays deterministic without the repository name. The scope listed the reducer too.
  - Unlink after a rename: `PullRequestUrl::forRepository()` refuses the old name, so the acceptance test needs a second rule. A GitHub unlink also takes a URL that equals a linked URL in any letter case. A link checks the URL against the current name and finds an earlier link by number, so it writes no duplicate.
  - The read job, not the link transaction, creates the record, before the permission check. So a delivery after `new_permissions_accepted` updates it. The job runs only when the link wrote an event; a repeated link reads nothing.
  - The job is skipped, without a token request, also for a repository without access and for a suspended installation, the cases in which GitHub cannot answer. A 404 leaves the record unchanged. Other GitHub failures fail the job, and Messenger retries it.
  - The permission check is in the read job only. The clone, the fetch, and the repository read of `installation_repositories.added` keep `contents: read` without a check, so installations from before the migration keep working.
  - `merged` comes from `merged_at`: the GitHub OpenAPI description (`github/rest-api-description`, read on 2026-10-13) does not require `merged` in the `pull_request` object of `assigned`, `labeled`, `synchronize`, and other actions, but every object has `merged_at`. `head.repo` is read null-safe, because a deleted fork has none.
  - The migration gives existing installations `permissions = {}`. The next sign-in or installation delivery records the accepted permissions; until then the read job is skipped.
  - `PullRequestState` is a closed set (specs README section 8), because GitHub has no other pull request states.
  - Live update `pull_request {type, reviewId, requestIds}` on the review topic, one per review that links the number, as `outdated`. A pull request can be linked in several reviews of a repository.
  - UI: `unknown` shows no label, so a local repository looks as before. The header shows the title next to the URL, and the thread shows only the label. The header link keeps the URL as its text, which the existing UI test reads.
  - The scope lists "the candidate in `features.md`" under docs. The brief forbids edits to `features.md`, so the candidate "Pull request links after a repository rename" is left for the orchestrator: F40 closes it.
  - The GitHub fixtures are not recorded from a real App. `pull-request-acme-billing-42.json` is the `pull-request` example of the GitHub OpenAPI description, changed to `acme/billing` #42. `webhooks/pull_request.closed.json` is that object closed and merged, with the `repository`, `installation`, and `sender` of `webhooks/push.json`. `webhooks/installation.new_permissions_accepted.json` and `installation-token-pull-requests.json` follow the existing fixtures. `pull-request-not-found.json` is the documented 404 body.
  - Verification with a real App is not done: no App exists yet. The status code and body of a token request above the accepted permissions stay unknown, and so no fixture keeps them.
  - For an installation that the tenant has already, `installation` `created` stores the new permissions on its row.
- **Review fixes:** an unlink returns the exactly linked URL before the number match, so a request with one number under two names unlinks the named URL (U `UnlinkPullRequestRulesTest`: "With one number linked under two names, the unlink removes the URL that it names"); architecture section 6 `unlink_pull_request` row, section 7.5 webhook events and review topic payloads, D53, and Q19 state the rule; R6 names the pull request records; `mcp.md` 4.15 errors use the Q19 wording; F `InstallationSyncTest` "Sign-in records the installations and the candidates" checks `permissions`.
