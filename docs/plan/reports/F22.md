## Report: F22 Quick open ranking

- **Status:** Done (awaiting merge). One commit `feat: F22 quick open ranking` on the worktree branch, rebased on `bd46b91`.
- **Summary:**
  - V16 also matches a name by word starts (D54): `CE` and `ComEx` find `CommandExecutor`, `HC` finds `HTTPClient`. A file matches by its path or by the word starts of its name, a symbol by its name.
  - The order puts word starts between the name prefix and the name substring, and orders each group by the length of the name before the length of the path. The wire format does not change.
  - The SQL of `IndexSql::search()` selects the candidates with an escaped `LIKE` pattern of the characters of `q` in order, next to the path substring for files. The pure class `Index\SearchRank` matches and ranks the streamed rows in PHP and keeps the first `limit`.
  - `SearchRank::top()` puts each row into its group of order rule 1 as it arrives. Each group keeps at most 2 x `limit` rows, and a row is not tested for the groups after those that already hold `limit` rows, so the memory of a request does not grow with the repository.

- **Decisions and deviations:**
  - A letter is `\p{L}`, a digit `\p{Nd}`, upper and lower case `\p{Lu}` and `\p{Ll}`. The split is one `preg_split()`. Symfony String's `snake()` is not used: it changes the case at word starts before it splits, and it counts only ASCII digits as digits, so it does not give the words of D54.
  - The word-start test compares the lower-case words and `q` byte by byte. A prefix that ends inside a character leaves a continuation byte at the start of the rest of `q`, and no word starts with one, so the result is the same as per character. A forward pass keeps, per offset of `q`, the lowest index of the next usable word, so a name of many words cannot make it backtrack exponentially. It runs in O(length of `q` x length of the name).
  - "Lengths count characters" is new in the V16 rules. F11 used the PostgreSQL `length()`, which counts characters, and the rank keeps that.
  - `SearchRank::top()` takes the SQL rows and builds `FileHit` and `SymbolHit` only for the first `limit` rows: `RepoPath::fromString()` for all 5,382 candidates of `e` took 4.5 ms. `IndexSql::search()` streams the rows with `iterateAssociative()`.
  - Each group keeps at most 2 x `limit` rows and is cut back to the first `limit` by order rules 2 to 5 when it is full. So a cut-back sorts 2 x `limit` rows once per `limit` new rows, and a row costs O(log `limit`) on average. A heap of size `limit` per group gives the same bound with an `SplHeap` subclass per call.
  - `pdo_pgsql` receives the whole SQL result into libpq memory, which the PHP `memory_limit` does not count: a result of 300,000 rows of 206 characters raised the resident memory of the process by 68 MB and the PHP memory by 0 KiB. For `e` here it is 5,382 rows. A cursor would bound it too, at one round trip per batch. It is in "Follow-ups".
  - The scope's case "`C-E` matches nothing" is `C-E` against `Command-Executor`: the words match after the `-` is removed, and the rule refuses `q`.
  - D48 keeps its text and adds "D54 amends the match and the order."

- **Follow-ups and new ideas:**
  - The candidate set grows with the repository: for a one-letter `q`, the SQL returns every name with that letter, 5,382 rows here, and the ranking time grows with it, about 94 ms for 130,000 synthetic candidates. The libpq buffer of the result grows with it too, outside the PHP `memory_limit`. A name index or a word-start test in SQL would bound the transfer and the time, and a cursor would bound the buffer. All are outside this scope.
  - PostgreSQL `lower()` and `mb_strtolower()` differ for a few characters, for example `İ`, which PostgreSQL lowers to `i` and PHP to `i` with a combining dot. A name with such a character can miss the candidate pattern. No file or symbol name of this repository has a character outside ASCII.
