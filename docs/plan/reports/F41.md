## Report: F41 Check run

- **Status:** Done (awaiting merge). One commit `feat: F41 check run` on the worktree branch `f41-check-run`, rebased onto `b9ce524`.
- **Summary:**
  - `CheckRunJob` creates or updates the check run `Slopmower (<login>)` of a tenant's pull request record on its head SHA, named with the GitHub login of the tenant's user, with the record ID as `external_id` and the request list of the review with the newest still-linked `pull_request.linked` as `details_url`. It stays `in_progress` while a linked request is unfinished, and completes with `success` when all are finished, or `neutral` without links.
  - Each unfinished anchored request located at the head SHA gives an annotation: `warning` for `open`, `reopened`, and `in_progress`, `notice` for `ready_for_review` and an agent's `wont_do`. The first 50 go with `POST`, the rest in `PATCH` calls of 50. The summary lists the linked requests per review with `N of M finished`.
  - A job whose status, annotations, or head SHA differ from the newest run creates a new run, as does a run older than 14 days and `check_run` `rerequested`. Otherwise the job updates the run without annotations. A head that the clone lacks gets one fetch, except a fork head, then a run without annotations whose summary says why.
  - Triggers: the request events of the scope through an `EventsCommitted` listener, a review deletion, a new head SHA or a reopen from the F40 record update, and `check_run` `rerequested`. A flag on the record and a 5-second `DelayStamp` give one job per record. A job holds the lock `check-run:<record ID>`, and its GitHub calls the lock `github-installation:<ID>`.
  - Check runs hold request headlines and links, never request text: an annotation has the headline as title and the state and link as message.
  - With `Repository.checkEveryPullRequest` on, which the session-only endpoint R8 and a switch on the repository screen set and which is off by default, a `pull_request` `opened`, `reopened`, or `synchronize` queues `NeutralCheckRunJob` for each tenant of the repository without a record of the number: a `completed` / `neutral` run "No linked requests" of that tenant's check on the head, so a user's required check never blocks a pull request that the user does not link. A `rerequested` run whose record is gone gets the same neutral run of the tenant that its name names.
  - `GitHubInstallation::accepts()` replaces `canRead()`: it checks the permissions of a job at their level, and `write` covers `read`.

- **Decisions and deviations:**
  - Check per tenant, decided by the orchestrator in review: with one name, the `success` or `neutral` run of one tenant hid the blocking run of another on the same head, so one user could lift another's gate. The check is named `Slopmower (<login>)` with the GitHub login of the tenant's user (`CheckRunOutput::name()`), and a repository requires the check of the user whose review gates the merge. A tenant without a GitHub user gets no run. After a rename of the login, the next run takes the new name, and the user replaces the required check.
  - Unlinked pull requests, decided by the orchestrator: on `pull_request` `opened`, `reopened`, and `synchronize`, each tenant with an active repository of `repository.id` and without a record of the number gets its own `NeutralCheckRunJob`. It posts a `completed` / `neutral` run of the tenant's check on `pull_request.head.sha` with the title and summary "No linked requests" and the `external_id` `tenant:<tenant ID>`, without `details_url`, annotations, or a record. A record of the tenant, from a link since the delivery, skips the job. The job, not the consumer, checks the installation, so the permission check stays in one place.
  - `check_run` `rerequested` of a run whose record is gone, for example after a deletion of the repository data or of the tenant (a review deletion keeps the `pull_request` rows): the consumer queues the neutral run on `check_run.head_sha` for the tenant that the `external_id` names, else for each tenant whose GitHub user has the login of the run's name, each only with the repository active. `check_run.pull_requests` gives the number when it names one, so the job still skips a tenant with a record. Without such a tenant, nothing.
  - Reopen: a record update that changes the state to `open` queues the job too, so a pull request reopened with the same head, or linked while closed, gets a current run.
  - Review deletion: `ReviewCommands::delete()` reads the records that the requests of the review link (`QueueCheckRun::linkedByReview()`) before the delete, and queues their jobs after the commit.
  - Race: a job holds the lock `check-run:<record ID>` from before it clears the debounce flag until after its last write, so an older, slower job cannot write after a newer one. The installation lock stays around the GitHub calls, inside the record lock. Every transaction inside the locks ends, by commit or rollback, before a release, as `config/packages/lock.yaml` requires.
  - Head: `RateLimited` from `fetchNow()` counts as a missing head, so the job posts a run without annotations instead of failing. A head repository that differs from the repository, or a deleted fork, gets no fetch.
  - Stale runs: GitHub Docs: "If a check run is in an incomplete state for more than 14 days, then the check run's conclusion becomes stale". The record stores the creation time of its run, and a run older than 14 days gets a new run instead of an update.
  - Shared head, second review: a check run belongs to a commit, and two open pull requests can share a head SHA. The neutral job posts nothing when the tenant has a record of the number or an open record on the head SHA (`PullRequestRepository::hasNumberOrOpenHead()`), on both the `pull_request` and the `rerequested` path, so a neutral run of an unlinked pull request never overrides the blocking run of a linked one on the same commit.
  - The neutral job reads those records inside the installation lock, after it is taken, so a record whose run came meanwhile counts.
  - Name in the hash: an update keeps the name of a run, so after a login rename an unchanged output would keep the old name and the new required check would never appear. `CheckRunOutput::hash()` takes the name, so a new name creates a new run.
  - Neutral `external_id`: a renamed login can pass to another user before the next sign-in of either, so two tenants can share a check name for that time. A neutral run carries the `external_id` `tenant:<tenant ID>`, and `rerequested` routes by `external_id` first: a record ID, then a tenant, and the login of the name only when the `external_id` names no active tenant. The user guide names the remaining collision of names as a limitation.
  - Privacy, decided by the orchestrator: on a public repository every check run is public, and GitHub has no call that deletes one. An annotation has the request headline as `title` and "<state> in Slopmower: <link>" as `message`, never the request text. The summary keeps the review titles, the headlines, and the links. The user guide says that everyone who can see the pull request can read the headlines.
  - Neutral runs are opt-in per repository, decided by the orchestrator: `Repository.checkEveryPullRequest`, off by default. Off, a tenant posts runs only for the pull requests that it links, and no neutral runs. On, the neutral runs of the review rounds. The value sits in the `github` object of `Repository`, because only a GitHub repository has check runs. It is set by the session-only endpoint R8 `POST /api/v1/repositories/{repositoryId}/check-every-pull-request` with `{enabled}`, which returns the repository, gives 422 `invalid_input` for a local repository, and publishes the live update `repository`. No MCP tool sets it. No input fixture exists, because the input fixture test runs on local repositories; `CheckEveryPullRequestTest` validates its body against `CheckEveryPullRequestInput`, and `ConnectGitHubRepositoryTest` expects the new field. The consumer queues neutral jobs only for repositories with the value on, and the job reads it again. The tests of the neutral runs switch it on in the database. The column is in the F41 migration, after F39's.
  - Cut test: "check_suite is github.ignored" duplicated the `github.ignored` case of `WebhookParsingTest`, through the same `HANDLED_EVENTS` fallback.
  - Required check source, decided by the orchestrator: no Statuses: write, D64 keeps the smallest permission set. GitHub Docs (read 2026-10-13): classic branch protection lets you "select an app that has recently set this check" and names no permission, and a ruleset app source needs the app "installed in the repository with the statuses:write permission". The user guide makes the check required through classic branch protection with the Slopmower app as source, and says to choose "any source" in a ruleset.
  - The migration is `Version20261013063000`, after `Version20261013044918` of F39.
  - "120 anchored requests" opens its requests in one transaction through `CommandExecutor`, as a batch of drafts does. 120 single opens queue 120 location recomputes, whose statements the Doctrine profiler of debug mode keeps, and the case took 412 MB of the 512 MB limit, which failed a later test of the full suite. Now it takes 142 MB.
  - New run on a changed status: the record keeps a hash of the status and the annotations, not of the annotations only. The REST description of `PATCH /check-runs/{id}` names no update from `completed` back to `in_progress`, so a reopen of a general request after `success` gets a new run instead of an update that GitHub may refuse. An update from `in_progress` to `completed` with the same annotations also gets a new run; the result on GitHub is the same.
  - `check_run` `rerequested` creates a new run (`CheckRunJob::$newRun`): GitHub Docs say that a re-run "requesting a new check run" goes to the App. The consumer queues the job without the debounce, because it writes no tenant row.
  - Closed pull requests get no check run job: the Goal names open pull requests. A run on the head of a merged pull request keeps its last state.
  - `details_url` is the request list `/reviews/{id}/requests` of the review, the list of the requests that the check is about. Without linked requests the run has no `details_url`.
  - A new head SHA queues the job from `PullRequestStateHandler::record()`, after its transaction, for the first read too. A link of a number without a record queues no check job from the link: the read job creates the record and then queues it with the head.
  - The 50-annotation groups are recorded only after the last call, so a failed job leaves the previous run in the record and its retry creates a complete new run.
  - The record has the extra column `checkRunRequested`, the debounce flag of the scope, as `Repository.fetchRequested` for `link_commits`, and `checkRunHash` for the comparison with the newest run. GitHub keeps the annotations, but reading them back would cost a paginated call per job.
  - `canRead()` is replaced by `accepts(array $permissions)`, which takes the same constant as the token request, for example `InstallationTokenProvider::CHECKS_WRITE`. The level order is `read`, `write`, `admin`.
  - `RequestState::closed()` moved its rule to `RequestStatus::isClosed()`, so `CheckedRequest::finished()` uses the same rule.
  - Test classes: the scope names `GitHubWebhookTest`; the webhook cases are in the new `CheckRunWebhookTest`, as the webhook tests are split per event. "Two quick request events give one job" is a case of `CheckRunJobTest`. "A job with the same status and annotations updates the run" is the extra case for the update rule.
  - `CheckRunJobTest` stores pull request 42 as a read at the head of main left it, newer than `pull-request-acme-billing-42.json`, so its head is in the clone. "A head that is missing" uses the recorded read, whose head is not in the clone.
  - The GitHub fixtures are not recorded from a real App. `check-run-created.json` and `check-run-updated.json` are the examples `check-run-example-of-in-progress-conclusion` and `check-run` of the GitHub OpenAPI description (`github/rest-api-description`, read on 2026-10-13), changed to `acme/billing` and the name `Slopmower`; the tests take the name from the request bodies, not from the fixtures. `webhooks/check_run.rerequested.json` is the example `check-run-rerequested` with the `repository`, `installation`, and `sender` of `webhooks/pull_request.closed.json`. `installation-token-checks.json` follows the existing token fixtures.
