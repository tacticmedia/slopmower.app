## Report: M21 Commenting UI

- **Status:** Done (awaiting commit).
- **Summary:** The code view shows the threads of the file inline and opens one comment box per file. The gutter "+" of `@pierre/diffs` opens the box for one line, a drag from the "+" opens it for a range in both directions, and the "+" takes a selection made on the line numbers (drag, or click plus shift-click). The box opens below the bottom line and receives the focus after its annotation slot exists. "Add single comment" posts Q2 through `useFetcher`, and the thread shows at once through `useOptimistic`; a reply posts Q4 the same way. The file header has "Comment on lines" (start and end line fields, D31) and "Comment on file", which also works on binary files. Markdown renders through `react-markdown` and `remark-gfm` with `markdown.css` of `@primer/css`; raw HTML shows as text. The "+" does not work with the keyboard; the result is in docs/architecture.md section 8.

- **Keyboard result of the gutter "+"** (task 5, `@pierre/diffs` 1.5.1): the library adds the `button[data-utility-button]` only under the mouse pointer, or on the last line of a selection. Without a selection it is not in the DOM, so the keyboard cannot reach it. With a selection, for example from `#L3`, Tab reaches it after "Copy path" (`tabIndex` 0). It has no accessible name (an icon only). Enter and Space do nothing, because the library starts a gutter comment on `pointerdown` and ignores `click` on the "+". So the "+" is not usable by keyboard; "Comment on lines" and "Comment on file" are the keyboard way (D31).
- **Deviations and decisions:**
  - Range gestures, by the orchestrator's decision: a drag or click plus shift-click on the line numbers only selects and writes `#L5-L9`, as M20 does for deep links. The "+" then sits on the last selected line (G1) and opens the box for the whole selection; a drag from the "+" opens it at once. Architecture section 8 flow 4 now says so. The acceptance gesture "click with shift-click" is click on 5, shift-click on 9, then the "+".
  - M20 follow-up: a comment range writes the line hash like any selection; submit and cancel clear the selection and the hash together (G1).
  - Threads per file: Q1 with `path`, `sort=path`, `limit=200`, all pages, filtered to the exact path (Q1 matches a prefix), then Q3 per request for its thread. No spec defines a thread list per file.
  - Threads show below the bottom line of their range, one annotation per line. File threads and the file comment box show under the file header, outside the code view, so they also work for files that are not renderable; the library's line-0 annotation is not used.
  - Annotation order, from the orchestrator's review: the library keys slot content by array index, so a line keeps its index while its file is shown. New lines are appended without sorting, and a line without threads stays as an entry that renders nothing until the path changes. A sorted array remounted the `ThreadBox` below a new line and lost its unsent reply.
  - `@pierre/diffs` 1.5.1 applies a changed controlled item only when its `version` changes (`CodeView.syncItemRecord()`); the annotations change through `items`, so `CodeFile` bumps `version` whenever it builds the item. The plan does not name this; without it no annotation appeared.
  - Busy state: `useTransition` `isPending` guards submit and open. The fetcher state is not usable while an async transition runs, because React renders its transition updates only when the action ends.
  - One comment box per file. A new "+", "Comment on lines", or "Comment on file" replaces it. While Q2 runs, opening is ignored. The box closes at submit, and the optimistic thread takes its place; when Q2 fails, the box opens again with the text and the error (the selection stays cleared). A reply box keeps its text read-only while Q4 runs, clears on success, and keeps it with the error on failure.
  - Read-only review: no "Comment on lines", no "Comment on file", no "+" (`enableGutterUtility` off), no reply box (Q3 `allowedActions` is empty).
  - `ThreadBox`: a status `Label` from `assets/requests/StatusLabel.tsx` (M22 lists that file; it exists now), the lines, then the entries that have a body. `request.opened` and `request.commented` show as comments; `request.released`, `request.ready_for_review`, `request.wont_do`, `request.reopened`, `request.verified`, and `commit.linked` with a body get a caption. Entries without a body, such as a claim, are left out. An agent gets an "Agent" label, a question a "Question" label. A user without an avatar gets a person icon, an agent a Hubot icon. The `ActionMenu` of a comment has "Quote reply".
  - Bundles: `FileRoute` loads through the route's `lazy` option, and its loader and action stay in the shell (`fileData.ts`). `ThreadBox` loads `MarkdownBody` lazily inside `Suspense`; the fallback shows the raw text, so the layout does not jump.
  - Writes go to the action of the `files/*` route as JSON `CommentIntent`: `{intent: 'open', input}` for Q2 and `{intent: 'reply', requestId, input}` for Q4. The result is the existing `ActionResult`.
  - "Comment on lines" is a Primer `AnchoredOverlay` with two text inputs (`inputMode="numeric"`, so `parseLineRange()` and not the browser validates). Its default focus zone is off: it is made for menus and took the fields out of the Tab order.
  - "Quote reply" focuses the reply box in the next animation frame, because the menu returns the focus to its button when it closes.
  - Skills: `make-test` (Panther for the browser behaviour, Vitest for pure TypeScript, `KernelTestCase` services for fixtures) and `cli-conventions` (`make` targets, `docker compose exec php` for filtered runs) applied. `services`, `configuration`, `components`, and `discover`: no PHP in `src/` and no configuration changed.
