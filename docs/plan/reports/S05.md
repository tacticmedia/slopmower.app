  - Handlers in three places: held, with a correction. `Application` had 4 handler methods (3 in `FetchRepository`, 1 in `PurgeTenant`), `MessageHandler` 2 classes, and `Webhook\Handler` 3 classes with 7 methods (`InstallationHandler` 5, `PushHandler` 1, `RepositoryHandler` 1). `debug:messenger` listed no other handler for `App\Message`.

- **Summary:** `FetchRepository` keeps the entry points that the rest of the code calls (`request()`, `queueClone()`, `fetchNow()`, `cloneReady()`, `readyClonePath()`, `removeAccess()`): 203 lines, 9 constructor parameters. `ServerClone` does the git work under the lock: `fetch()` builds the source command, with the installation token or the local discovery, and records success or a redacted failure; `synced()` dispatches `RepositoryFetched`, then `RepositoryChanged`. `RepositoryLock::acquire()` holds the polling wait that `fetchNow()`, the jobs, and the clone deletion share. All 13 handlers are in `App\MessageHandler`. The GitHub connect lives in `RepositoryController::connectGitHub()`, and its lock key in `InstallationSync::lockKey()`. `src` keeps 399 files and loses 39 lines; `tests` loses 1 file and 12 lines.

- **Deviations and skips:**
  - The ledger's interface for the two fetch commands: skipped, because only `ServerClone` picks the command, so an interface and a picker in `App\Source` add a file and a single-consumer service. Instead the two classes are one `Source\FetchCommand` with the factories `gitHub()` and `localDirectory()`: one file and 19 lines fewer. The "installation suspended" message is a private constant of `ServerClone`, its only user.
  - `FetchCommand` has one consumer, `ServerClone`, and stays a class: it is a readonly value object, not a service, and it keeps the D38 extraheader and the upload-pack quoting unit-testable in `FetchCommandTest`. Folding it into `ServerClone` would not be smaller.
  - `RepositoryLock` takes the clock and the polling wait. Without it, `ServerClone` or each lock holder would need the poll loop; `RepositoryLock` already was the one place of the lock key.
  - Clone and fetch jobs share one class, `RepositorySyncHandler`, and the clone deletion and the tenant purge share `DeletionHandler`. One class per message would need a shared home for the job timeout and for `deleteClone()`, which is a single-consumer service or a handler injected into a handler.
  - `app:tenant:purge` calls `DeletionHandler::purge()`. A separate `PurgeTenant` service would leave a forwarding handler.
  - The three GitHub handlers are renamed after their messages (`GitHubPushHandler`, `GitHubInstallationHandler`, `GitHubRepositoryHandler`), because `RepositoryHandler` next to `RepositorySyncHandler` names the wrong job.
  - `lockKey()` lives in `GitHub\InstallationSync`, the main holder of the lock and the namespace of the GitHub rows that it guards. `RepositoryHandler` and `InstallationHandler::locked()` stay separate (S11 finding).
  - `ConnectedRepository` stays in `App\Application`, now with one user, `RepositoryController`. A tuple return of the two connect methods would remove its file but lose the `created` name.
  - `config/reference.php` is regenerated by the cache warmup. It is not part of this commit.
- **Follow-ups:**
  - S13: the import graph loses four two-way edges: `Application` and `Message`, `Message` and `MessageHandler`, `Message` and `Webhook` (all docblock imports of handlers), and `Entity` and `Webhook`. The 13 cycles that the guide lists stay.
