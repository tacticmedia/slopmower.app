## Report: F56 Known issues of F54

- **Status:** Done (awaiting merge). One commit `feat: F56 known issues of f54` on the worktree branch `f56-known-issues`, from `9350c0c`.
- **Summary:**
  - The loop of `GitHubInstallationHandler::handlePermissions()` is now `QueuePullRequestRefresh::ofInstallation(int $installationId, bool $readEvery, bool $checkRuns)` in `App\Application`. For each `active` repository of the installation, it queues a `ReadPullRequestJob` for each linked pull request, every one or only one without a read state, and with `$checkRuns` `QueueCheckRun::request()` for each record.
  - `handleSuspension()` returns from the lock whether the tenant has the installation row. After an `unsuspend`, it calls `ofInstallation(readEvery: true, checkRuns: true)`. A `suspend` queues nothing.
  - `InstallationSync::record()` reads the stored installations before it deletes them and returns, for each listed installation that adds Pull requests: read or Checks: write, whether Checks: write is new. A listed installation without a stored row had no permissions. After `GitHubRepositoriesLock::run()` returns, `sync()` calls `ofInstallation(readEvery: false, checkRuns: <Checks: write is new>)` for each.
  - `handlePermissions()` keeps its comparison and calls `ofInstallation(readEvery: false, checkRuns: $checksAdded)`.

- **Decisions and deviations:**
  - A new class `QueuePullRequestRefresh`, because no existing class fits: `QueueCheckRun` queues only `CheckRunJob` on the check run triggers, and a new Pull requests: read queues reads without a check run. It has two consumers, the handler and `InstallationSync`.
  - The comparison "new permission" stays in each caller: `handlePermissions()` compares one row before and after `recordPermissions()`, and `InstallationSync` compares the stored rows with the listed ones before it deletes the rows. `GitHubInstallation::getInstallationId()` is new, so `InstallationSync` can match them.
  - An unsuspend queues only when the tenant has the installation row and is not being deleted, as `handlePermissions()` does. It queues also when the row was not suspended, for example after a lost `suspend` delivery, because the scope decides "every linked pull request" without a condition.
  - Test support: the setup of `PermissionsAcceptedTest`, its permission constants, and its queue helpers moved into the trait `LinkedPullRequests`, which the three classes share. `linkPullRequests()` returns the `User` instead of the `TenantId`, because the sign-in sync takes the user, and it takes an optional `suspendedAt`.
  - Docs beyond the scope list: the `App\Application` row of the developer guide, whose file count the new class changes. D64 in architecture section 11 stays, because F56 adds no contract and D64 does not say that only `new_permissions_accepted` queues the jobs.
- **Follow-ups and new ideas:**
  - A sign-in records the listed `suspended_at`, but a listing that clears a stored suspension (a lost `unsuspend` delivery) queues no reads or check runs. Candidate "Pull request states after a missed unsuspend".
