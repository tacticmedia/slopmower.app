## Report: F53 Worker and MCP diagnostics

- **Status:** Done (awaiting merge).
- **Summary:**
  - MCP errors: the catch-all of `McpTools::run()` logs the error, captures it through `Sentry\State\HubInterface`, and answers `internal_error`. The hub is an optional constructor argument: autowiring injects the bundle hub in `prod` and `null` elsewhere. The event goes through the client of the bundle, so the F51 `data_collection` options and `SentryClientErrorFilter` apply. A `DomainError` of a tool sends no event.
  - Idle log line: `Kernel::process()` gives `messenger.transport.doctrine.pg_notify_on_idle_listener` the logger `monolog.logger.messenger_idle`. `monolog.channels` declares the channel, and the handlers `main` and `console` of `dev` and `prod` leave it out.
  - Idle memory: the dev worker grew by about 37 KB per idle poll, one poll per second, so it reached `--memory-limit=96M` after 11 to 30 minutes. Cause: Messenger's `ResetServicesListener` resets the services only after a handled message, and in debug mode the Doctrine `BacktraceDebugDataHolder` keeps 5 queries with backtraces per idle poll (about 35.8 KB). The traced event dispatcher and the stopwatch keep about 1.4 KB more, and other services with a reset about 0.6 KB. `App\Messenger\IdleWorkerResetListener`, `#[When('dev')]`, calls the services resetter after each idle poll. `prod` runs without debug and does not grow.

- **Decisions and deviations:**
  - The listener gets its logger through `Kernel::process()`, which `Kernel` already uses for vendor services. A `monolog.logger` tag would come too late there, because the kernel pass runs at priority -10000, after `LoggerChannelPass`. So the pass replaces argument 0, the `logger` reference, with `monolog.logger.messenger_idle`, and `monolog.channels` creates that logger. No YAML redefinition of the vendor service.
  - The `test` and `e2e` handlers keep the channel. No test and no `e2e` process runs a worker on a PostgreSQL transport.
  - `SentryClientErrorFilter` is unchanged. For a tool error under `/_mcp`, `ApiExceptionListener::status()` gives 500 for each exception that the catch-all sees, except a security exception in the chain (401 or 403) and an `HttpExceptionInterface` with a status below 500. No tool throws these: the MCP firewall authenticates before the tool runs, and the tool code throws `LogicException`, DBAL, and runtime exceptions. Such an event would be dropped as D67 says.
  - The memory fix is in `dev` only, because only debug mode grows. `--no-debug` for the dev worker was rejected: without debug the kernel does not rebuild a stale container, so the worker would miss a configuration change after `make worker-restart`.
  - The reset runs after each idle poll, once per second. It is the reset that Messenger runs after each message.
  - The test environment registers `Sentry\State\HubInterface` as `RecordingHub`, a subclass of the SDK `Hub` that keeps each captured exception, as it registers the GitHub mocks. It is not a replacement: the hub does not exist in `test` otherwise.
  - `ProdContainer` became `EnvironmentContainer`, and `ProdLogChannelsTest` became `LogChannelsTest`, because the channel test also builds the `dev` container. The containers build without debug. Channel wiring does not depend on debug.
  - The scope names the two candidates in `features.md` under Docs. The orchestrator owns `features.md`, so this branch does not change it.
- **Follow-ups and new ideas:**
  - Upstream: no issue found for an idle worker that grows in debug mode. `ResetServicesListener::resetServices()` skips the reset when `isWorkerIdle()`, by design.
