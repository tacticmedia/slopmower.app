## Report: M31 Data deletion and tenant purge

- **Status:** Done (awaiting commit).
- **Summary:** V13 deletes a review with all its rows in one transaction under the tenant row lock, then its review pin and the commit pins that no remaining link uses, and publishes `repository`. R6 deletes a repository with all its rows, the index, the location cache, and its scoped tokens in the request under the same lock, publishes `repository_deleted`, and queues M33's `DeleteCloneJob`. A2 revokes all tokens and marks the tenant in one transaction, ends the session so that the response clears the cookie, and queues `PurgeTenantJob`. `PurgeTenant` deletes every tenant row and the tenant directory; `app:tenant:purge` runs it for an operator. The sign-in lookups refuse a tenant that is being deleted in one place, `UserRepository`. Index, location, and GitHub writers lock their parent rows, so no row outlives its deletion. The review header and Settings have the three dialogs.

- **Deviations and decisions:**
  - Jan's rule (no service class with one consumer) over the plan's file list: no `DeleteReview`, `DeleteRepositoryData`, or `DeleteAccount` class. V13 is `ReviewCommands::delete()` beside `start()`, which writes the review pin. R6 and A2 live in their controller actions, which call `CommandExecutor`, `DeletionSql`, and the bus. `PurgeTenant` has two consumers: its `#[AsMessageHandler]` method and the command. It holds the handler, as `FetchRepository` does, so there is no `src/MessageHandler` class.
  - R6 queues M33's `DeleteCloneJob` (orchestrator decision) instead of the plan's `DeleteRepositoryFilesJob`. Its handler calls the new public `FetchRepository::deleteClone()`, which the purge also uses for each clone under its repository lock, and then deletes the index and the location cache of the repository (orchestrator decision), so access removal matches architecture section 4. For R6 these deletes find nothing.
  - Raw deletes: one `final` class `DeletionSql` with statement lists in foreign key order (review, repository, repository index, tenant). Every statement names `tenant_id`, or `id` on `tenant` (`RawSqlTenantAuditTest`). Tokens go before users and repositories, because the M14 foreign keys have no `ON DELETE`. R6 deletes the scoped tokens (docs/specs: "deletes ... the tokens scoped to the repository"), not only revokes them. GitHub candidates stay at R6, because the installation does not change; the purge deletes them with the installations. Each method runs in a transaction of its own, or in a savepoint of the caller's.
  - Parent row locks (orchestrator review): each deletion starts with `SELECT ... FOR UPDATE` on its parent rows (the review; the repository and its reviews; the repository for the clone job; all repositories and reviews of the tenant), so a draft or viewed-file insert, an index write, and a location cache write wait for it. `IndexSql` locks the repository; `LocationCacheSql` locks the repository and then the review of the `request.opened` event, in the order of the deletions, so they cannot deadlock. Both skip their writes when the row is gone or the access is removed. They lock FOR KEY SHARE instead of FOR SHARE: a delete and FOR UPDATE wait for it, but the sync state updates of the repository row do not.
  - The tenant row lock: `CommandExecutor::delete(TenantId, Closure)` runs the closure through `transactional()`, the M07 lock and transaction rules, and clears the entity manager afterwards. It takes the tenant ID, because the purge command has no tenant context.
  - V13 reads the commit SHAs of the review's links under the lock, before the delete. After the commit, when the clone directory exists, it deletes the review pin and each commit pin that `isLinkedInRepository()` no longer finds. A git failure there is logged as a warning, as in `UnlinkCommit`. The check runs after the commit, so it has the M16 pin race of `UnlinkCommit`.
  - The A2 mark is `tenant.deletion_requested_at` (nullable time). The sign-in lookups, and the GitHub webhook consumer and jobs, read it. `UserRepository::signInUser()`, the one place for the sign-in, joins the tenant and throws `TenantBeingDeleted`, a `CustomUserMessageAccountStatusException` ("The account is being deleted."), so the local sign-in page shows the message and the GitHub provider does not create a second tenant for the same GitHub user. `findLocalByLogin()` and `findByGitHubUserId()` replace the `findOneBy` criteria of `LocalUserProvisioner`, `GitHubUserProvider`, and the e2e sign-in. `TenantUserProvider` turns `TenantBeingDeleted` and a missing user or tenant row into `UserNotFoundException`, so `ContextListener` signs out every other session at its next request. `ApiTokenHandler` also checks the owner through `findSignedIn()`, so a token that a concurrent T2 created after the revoke cannot authenticate either.
  - GitHub webhooks (orchestrator review): the consumer routes no job to a tenant that is being deleted. `InstallationHandler` locks the tenant row FOR SHARE (`TenantRepository::lockActive()`) in its write transaction and skips a tenant that is gone or marked; FOR SHARE, because FOR KEY SHARE would not wait for the A2 mark. `PurgeTenant` runs the idempotent `deleteTenant()` also when the tenant row is gone.
  - A2 ends the session with `Security::logout(false)` and `Session::invalidate()`. `SameOriginCsrfListener` writes its check strategy into the new session on `kernel.response`, which made the session listener send a new session cookie instead of clearing it. The action removes the request attribute that triggers that write (named by the stateless token value of `ApiCsrfListener::TOKEN_ID`), so the response clears the session cookie. Without the attribute the listener also skips the double-submit cookies, so the action clears them on the 202 response as the listener does.
  - `confirm` is a `#[MapQueryString]` DTO with `#[Assert\NotNull]`, so a missing value is 422 on `confirm` after the 404 of the path ID and the 403 of the actor kind. The comparison is exact (case-sensitive).
  - The purge: rows first, in one transaction under the tenant row lock, including the tenant row; then each clone under its `RepositoryLock`, so a running fetch finishes first; then the tenant directory. A retried job or a second command run deletes what is left, also without the tenant row. Its reads (the tenant row, the repository IDs) run inside `TenantFilter::suspend()`, the purge place of the four, so the job and the command share them.
  - `CrossTenantCases` gets an optional `query`, because the inventory requires the route path, and A2 and R6 take `confirm` in the query. A case without a schema and without IDs (A2) must answer its status with an empty body.
  - UI: "Delete review" shows for open and closed reviews. The review action redirects to the repository page. Settings gets a "Repository data" table with "Delete data" per repository, and a "Delete account" section. Both use `TypedConfirmationDialog`: the danger button works only when the typed text equals the name or the login, and the dialog does not close while the write runs. The account action loads `/login` as a new document (`redirectDocument`), as the sign-out route does. The GitHub App note shows only for a GitHub user.
  - Tests: `DeletionFixtures::populatedReview()` runs the queue after V1 and Q2, because the next request reboots the kernel and drops the in-memory queue (M26 gotcha). "The same directory connects again before the job runs" shows the connect while the old clone still exists; the job itself runs in "The job deletes the clone". The plan's "The IDs of the review and its requests answer 404 afterwards" also checks a draft ID, as the scope says. `DeletionRaceTest` holds a `DeletionSql` deletion open on a second connection and proves the wait with `lock_timeout` (SQLSTATE 55P03). The local sign-in refusal is a call of `LocalUserProvisioner`, because the local sign-in route exists only in `dev`.

- **Risks discovered:**
  - A draft (D2) or viewed-file (V12) insert that waits for a V13 or R6 delete fails afterwards with a foreign key violation, a 500, because the review is gone.
  - An index write holds the repository row FOR KEY SHARE for its whole transaction, so a large first `insertFiles()` delays an R6 of the same repository until it commits.
  - The `RepositoryLock` wait of `deleteClone()` has no limit, as in M33. A hung fetch holds the purge job.
  - A2 with `sync://` in `e2e` runs the whole purge inside the request.
