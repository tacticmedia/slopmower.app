- **Decisions and deviations:**
  - Step 4 is done while T1 lists an active token, not any token: T1 also lists revoked and expired tokens, which connect no agent. "A revoked token leaves step 4 to do" covers this rule.
  - "Show closed reviews": the hidden empty review list took its "Show closed" checkbox along, so a repository with only closed reviews had no way to list them. The link sets `?state=all`, which shows the list with the checkbox checked. `docs/user/reviewing.md` names it.
  - "Start a review" comes first in the document order. From 1012 px the steps are a 320 px side column, so they show next to the form. Below 1012 px they follow the latest commits.
  - Both forms show the same content: the marker, the title, the sentence, and "Learn more". The compact form has smaller markers, type, and spacing, and no actions. Each form has the heading "Getting started, step n of 4" (`h2`), and each step title is an `h3`.
  - `OnboardingSteps` takes `form`, `tokens`, and `actions`. The full form shows only while no repository is connected and the compact form only on a repository, so the state of step 1 follows from the form, and steps 2 and 3 are never done while the steps show.
  - The candidates of step 1 are a bordered list with the name, the details ("Private, installed on acme", "HEAD branch main"), and the existing `CandidateConnection`, which gets the hidden field `openRepository`. The list scrolls inside the step above 22 rem, because R2 can give 1,000 candidates.
  - "Add repositories on GitHub" links to `githubConfigureUrl` of R2 and shows only while it is not null. The no-source banner is a Primer `Banner` with an `h4` title, so the heading levels stay in order.
  - The loaders keep T1 as `tokens: ApiToken[] | null`: null means the steps do not show, so T1 was not read.
  - `docs/user/getting-started.md` has one `h2` per step, IDs `1-connect-a-repository` to `4-connect-your-agent`, checked on the dev site. The sign-in is a paragraph above step 1. Step 1 keeps the GitHub App, the plan limit, and the Marketplace paragraphs.
  - `FakeRepositories` owns a `FakeTokens` as `tokens`, because both repository screens now read T1. The specs that made their own `FakeTokens` use it, so T1 to T3 have one set of routes. The fake also connects GitHub candidates, which the acceptance test needs.
  - Existing specs that visited `/repositories` for the tables connect one repository first. The Shell test "Client-side navigation keeps a window marker" navigates to Settings, because `/` now opens Repositories. `MockedResponses` registers `FakeRepositories`, because `/` loads R1 after the redirect.
  - `VerticalSliceTest` connects in the first step, waits for `/repositories/*`, and starts the review there. `SignInTest` is unchanged.
