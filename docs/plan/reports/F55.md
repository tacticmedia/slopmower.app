## Report: F55 Flaky tests under load

- **Status:** Done (awaiting merge). One commit `feat: F55 flaky tests under load` on the worktree branch `f55-flaky-tests`, from `75273b5`.
- **Summary:**
  - `ChangesTab` "A file loads its diff when it scrolls into view": a race in the code. `@pierre/diffs` draws no row until the worker pool of the page is ready. Until then a loaded file had the height of its header, so the files below came near the window and loaded too. Under load all four files loaded before the scroll. `SidesDiff` now keeps the pending height until the view has a `[data-line]` row.
  - `HubIsolationTest`: a race in the test. `stream($source, 0.1)` yields a timeout chunk after 0.1 s without data. The loop did not check it, so it threw "Idle timeout reached" instead of waiting the 2 s of the test. The stream now has the 2 s as its idle timeout, and the loop checks `isTimeout()`.
  - The `make act` group of 2026-10-15 (rows of the code view after 5 s): only slow. Each test waits for a row with an assertion, and the row comes after the worker pool of the page is ready. In the Linux VM under load, the same tests fail at an assertion timeout of 1 s and pass at 5 s. `playwright.config.ts` now has `workers: 4` and `expect.timeout` 10 s.
- **Reproduced load:**
  - Host: `yes > /dev/null` processes (24 or 40), and a second UI suite on its own port and a copy of the build (`var/f55/run-pair.sh`, with its own config in `var/f55/`), so 2 suites ran at once.
  - Linux, as in the act job: the UI suite in the `php` container (Chromium 1243 of the image, `@playwright/test` 1.63.0 of the checkout) against a `vite preview` of the build on the host at `host.docker.internal`, with 32 to 128 `yes` processes in the same container. The two clipboard tests are left out there, because that origin is not a secure context.
  - The load average is the 1-minute value of `uptime` at the start and the end of each run. Other projects' stacks and a peer session ran on the host the whole time, so the load also changed without the stress of these runs. The VM stress raises the macOS load average far more than the CPU use: 64 processes in the VM gave 66 to 330.

- **Decisions and deviations:**
  - **Workers 4.** With 2 suites on the host, 4 workers each finish sooner than 8 (33 s against 37 s). Without stress, 4 workers cost 2 to 5 s against 8. In the VM under CPU stress, 4 workers run longer (85 to 89 s against 62 to 63 s), and they halve the slow assertions: at a 1 s limit 10 failures against 20, at 2 s no failure in 3 runs against 3 failures in 3 runs.
  - **`expect.timeout` 10 s.** The longest assertion wait under the reproduced load is between 2 and 5 s, and the act run of 2026-10-15 went past 5 s. `CodeFile` waits `MAXIMUM_SCROLL_WAIT_MS`, 10 s, for the view to know its lines, so a longer limit gives a test of a line hash nothing.
  - **No retries**, as the scope says.
  - **The row check in `SidesDiff`.** A first version removed the pending height at the first `onPostRender`, and 42 of 48 runs still failed: `hydrate()` also reports the empty render of the mount. The height now goes only when the view has a `[data-line]` row.
  - **The act group was not reproduced at the 5 s limit.** CPU stress alone, up to 128 processes in the VM, did not take any wait past 5 s. The same tests fail at 1 s. The orchestration state of 2026-10-15 records 11 GiB free on the host disk that day, which these runs do not reproduce. The act output of that run is overwritten, so the list of tests in the scope is not verified.
  - **ChangesTab, the second test** of the act run is not known. The code fix covers each test of `ChangesTab` that loads a file above or below another.
  - **`HubIsolationTest` before the fix did not fail under load** in 30 runs. A mutation shows the cause: without A's update, the old loop threw "Idle timeout reached" after 0.26 s. With the fix, the same mutation fails the assertion after 2.2 s.
  - **Browser launch** at a load above 100 (F53) is out of scope. No launch timed out in these runs, up to a 1-minute load of 340 in the VM.
  - **Stress periods:** each one lasted at most 10 minutes, except the PHP run, whose stress lasted 10.3 minutes.
  - **Library documentation:** the context7 quota was used up, so the `@pierre/diffs` 1.5.2 and `symfony/http-client` behaviour comes from their installed sources.
  - The candidate "Flaky tests under load" in `docs/plan/features.md` stays for the orchestrator, as the feature brief says.
- **Follow-ups and new ideas:**
  - `CodeFile` stops the scroll to a line hash after 10 s without line positions, so on a host where the worker pool takes longer the view stays at the top. Not seen in these runs.
  - Each page starts its own worker pool with 2 workers and a highlighter on the main thread. That is the start-up cost of each UI test with code. A pool size of 1 in the UI build could lower it.
