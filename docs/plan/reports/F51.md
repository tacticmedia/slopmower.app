- **Decisions and deviations:**
  - **Query parameters.** The REST API has `confirm` (A2 login, R6 repository name), `name`, `source`, `limit`, `cursor` (R1), `source`, `q`, `includeConnected` (R2), `state` (V2), `dir`, `recursive` (V6), `path` (V7, V8, V9, V14, V17, Q1), `line`, `column`, `name` (V14), `q`, `limit` (V16), `cursor`, `limit`, `includeOwn` (V10), `status`, `awaiting`, `outdated`, `suggestion`, `sort` (Q1), `at`, `context` (Q3). Outside `/api/v1`: `download` (skill file), `_target_path`, the OAuth `code` and `state` of `/login/check-github`, and `installation_id` and `setup_action` of `/github/installed`. A user or an agent types `q` (V16 search text, R2 name filter), `name` (R1 repository name, V14 PHP name), and `confirm` (the GitHub login or the repository name), so their values are `[Filtered]`. `code` is the OAuth code, a credential. The others are closed sets, numbers, IDs, SHAs, cursors, and file paths. File paths stay: the shell URLs `/reviews/{id}/files/{path}` hold them too, and the scope keeps the URL. A cursor encodes sort keys, so it can hold a repository name (R1) or an anchor path (Q1 `sort=path`). The SDK matches a term as a case-insensitive substring of the key, so a later key that contains `q`, `name`, `confirm`, or `code` is filtered too. Removing every query string was not chosen, because `path`, `cursor`, and the filters help an operator to repeat a failed request.
  - **`before_send` only, no new `ignore_exceptions` entry.** `ignore_exceptions` matches the class of each exception in the chain and cannot see a status: `HttpExceptionInterface` would also drop the 503 of `SessionLockedMcpController`, and `DomainError` would drop an exception whose `ErrorCode` maps to 500. The two recipe entries for fatal errors stay, because the fatal error integration reports them.
  - **Status mapping.** The bundle captures at `kernel.exception` priority 128, before the firewall (1), the framework log listener (0), which maps the `#[WithHttpStatus]` of the security exceptions, and `ApiExceptionListener` (-1). `ApiExceptionListener::status(\Throwable, Request)` gives the status that they answer: a security exception anywhere in the chain gives 401 or 403, as the firewall walks the chain and answers with 401, 403, or a redirect to the sign-in; under `/api/v1`, and for `rate_limited` on every path, a `DomainError` gives the status of its `ErrorCode`, an `HttpExceptionInterface` its status if `HTTP_STATUSES` holds it, else 500; outside, an `HttpExceptionInterface` gives its status, as the framework answers it; every other exception gives 500. `ApiExceptionListener` takes its own statuses from that function. `HttpKernel::handle()` wraps each `RequestExceptionInterface` into `BadRequestHttpException` before `kernel.exception`, so an invalid `Host` gives 400. Not modelled: a security exception on the paths without a firewall, `/docs` and `/webhook/`, where no code throws one.
  - **Events without a request.** The callback reads `RequestStack::getCurrentRequest()`, not the `request` of the event: the request integration sets no `request` when the PSR-7 conversion fails, for example for an invalid `Host`, and such an event would go out. The stack holds the request during `kernel.exception` and is empty in a Messenger worker, in a console command, and between the requests of a FrankenPHP worker. An event without a current request goes out, also for a `DomainError` with a 4xx code: a worker or a console command sends no response, so the error is a server error.
  - **`tracing: false`, beyond "Tracing is off without `traces_sample_rate`".** With the default `tracing.enabled`, the bundle decorates the DBAL driver, the cache pools, Twig, and the HTTP clients, and the HTTP client adds `sentry-trace` and `baggage` headers to every outgoing request, also to GitHub and the symbols service. The baggage holds the public key of the DSN, the release, and the environment. The scope decision "no tracing" covers this.
  - **`database_query_data: false`, `queues: false`, and `gen_ai: { inputs: false, outputs: false }`, beyond the scope list.** With `data_collection`, every option that is left out collects. In 4.34.0, `database_query_data` applies only to database spans, no code reads `queues`, and the application sends no AI spans, so all three are guards for an SDK update.
  - **Forwarded IP headers.** In `data_collection` mode, the `RequestIntegration` that the bundle builds has no `pii_sanitize_headers`, so `X-Forwarded-For` and `X-Real-IP` would go out in clear. The header deny terms `forwarded`, `x-real-ip`, `client-ip`, and `connecting-ip` filter them, also `Forwarded`, `True-Client-IP`, and `CF-Connecting-IP`, and `X-Forwarded-Proto` and `X-Forwarded-Host` as a side effect. The SDK deny list filters `Authorization`, the CSRF header, and `Mcp-Session-Id`, and drops `Cookie`.
  - **Messenger.** `MessengerListener` tags an event with `messenger.message_class`, `messenger.receiver_name`, and `messenger.message_bus`, and sends each exception that a `HandlerFailedException` wraps as its own event. It does not serialize the envelope. With frame variables off, the message object and its strings are not in a frame either. The exception messages are those of the prod log.
  - **Console.** `ConsoleListener` adds the extra `Full command`. In `data_collection` mode, the SDK filters the values of options whose names match its deny list, for example `--password`.
  - **Recipe comments.** `sentry.yaml` loses the commented Monolog examples and the `send_default_pii` hint: `data_collection` ignores `send_default_pii`, and the scope rules out the Monolog handler.
  - **`ProdContainer`.** `tests/Support/Environment/ProdContainer.php` holds the prod container build of `ProdLogChannelsTest`, so both tests share it. A compiler pass makes the named services public, because `ContainerBuilder::get()` refuses a private service and the bundle registers `sentry.client.options` only during the compilation.
  - **Docs.** `SENTRY_RELEASE` is in the deployment docs: without it, each event has the release `1.0.0+no-version-set`. The deployment docs also name the data scrubbing of the Sentry Security & Privacy settings and the setting that stops storing IP addresses as a second layer. The Sentry docs do not give the exact labels, so the docs name them generally. The privacy policy also changes the CCPA purposes and categories and the security line, which named only GitHub, the hosting provider, and logs. A report URL can hold a repository name through `cursor`, the base64url JSON of the sort key (`Http\Cursor`, `RepositoryQuery`), and the 503 of `SessionLockedMcpController` is a refusal that sends a report, so the policy promises no report only for a refusal because of the request itself. Architecture section 9 lists no external services, so it is unchanged. The developer guide counted 71 unit, 181 functional, and 7 E2E classes before F51. It counts 74, 187, and 9 now.
- **Follow-ups and new ideas:**
  - A server error inside an MCP tool never reaches `kernel.exception`: `McpTools::run()` logs it on the `app` channel and answers `internal_error`. So it is in the prod log, but not in Sentry.
