## Report: F12 Index job memory

- **Status:** Done (awaiting merge).
- **Summary:**
  - The job kept nothing between files. In debug mode (`dev`, `test`), DoctrineBundle's `DebugMiddleware` keeps every statement of one Messenger message until the message ends, with its parameters and a backtrace (`profiling_collect_backtrace: '%kernel.debug%'`). The job wrote each PHP blob in its own transaction: 5 statements per blob, about 84 KB per PHP file in the dev worker and about 120 KB in the test environment.
  - The job now parses without a write and writes the parsed blobs in batches of about 1,000 rows, and before each progress publish. `IndexSql::insertBlobs()` writes a batch in one transaction: the `FOR KEY SHARE` lock, one multi-row blob insert with `ON CONFLICT DO NOTHING RETURNING blob_sha`, and the symbols of the returned blobs only.
  - Dev worker, this repository, `app:index:rebuild --reparse`: peak 91.4 MB before, 45.3 MB after, from 28.9 MB at the start. Without the debug middleware, the job was flat before and stays flat.
  - No PHP memory limit is raised. The worker's Messenger limit goes from 256M to 96M, below the 128M PHP limit, so the worker stops after a message before PHP fails.
- **Files:**
  - Back end, changed: `src/Index/IndexSql.php` (`insertBlob()` becomes `insertBlobs()`), `src/Index/BlobSymbols.php` (`parse()` does not write, `of()` writes the blob it parses), `src/MessageHandler/IndexReviewHandler.php` (batches).
  - Configuration: `compose.yaml` (worker `--memory-limit=96M`, with a comment that names the 128M PHP limit).
  - Tests, created: `tests/Functional/Index/IndexMemoryTest.php`. Changed: `tests/Functional/Index/IndexReviewHandlerTest.php`, `tests/Functional/Tenancy/RepositoryScopeSqlFilterTest.php`.
  - Docs: `docs/developer-guide.md` (flow 4.1, step 12; section 7 rows Message handlers, 7 classes, 762 lines, and Symbol index, 10 files, 937 lines), `docs/plan/README.md` (gotcha "Doctrine profiler in the worker").
- **Tests added:**
  - F `IndexMemoryTest`: "Indexing 1,500 new PHP files after the first files grows the peak memory by less than 64 MB". It indexes 100 PHP files first, then resets the peak and indexes a commit with 1,500 more. Measured peak growth: 39.5 MB in three runs. The old code: 187.5 MB, and the test fails. The job writes about 12 batches, so the test also asserts 1,600 `indexed_blob` rows, 11,200 `symbol` rows, and `symbolsTotal` 11,200. With the final batch write removed, it fails with 1,500 and 10,500.
  - F `IndexReviewHandlerTest`, "Two index jobs at one commit write each row once", changed: a batch of one stored blob and one new blob writes the new blob and its symbol only. `symbol` has no unique key, so a write for the stored blob would duplicate its rows.

No file in `docker/frankenphp/conf.d/` sets it. `compose.yaml` ran the worker with `messenger:consume --memory-limit=256M`, which Messenger checks against `memory_get_usage(true)` only after a message, so it never stopped the worker before PHP failed.

- **Decisions and deviations:**
  - The cause is outside the job code, so the fix reduces what the profiler keeps: one batch write instead of one transaction per blob. In `prod`, which has no profiler, memory stays flat. In debug mode, memory still grows by the parameters of the writes, about 7 KB per PHP file. "Flat" in the scope holds for `prod` only.
  - `profiling_collect_backtrace` and the `test` configuration stay. `BearerAuthenticationTest` reads the `db` collector, and the web profiler shows the backtraces.
  - Not chosen: a worker with `--no-debug`, because a container that is not in debug mode is not rebuilt after a configuration change. A reset of `doctrine.debug_data_holder` from the job, because it ties production code to a profiler service. A job split into several messages, because the `e2e` `sync://` transport and the `QueuedMessages` trait reset no services between messages.
  - `IndexSql::insertBlob()` returned a bool that only a test read. `insertBlobs()` returns nothing, and the row counts of the test prove the rule.
  - A batch sorts its blob rows by SHA, so two writers wait for their common blob keys in one order and cannot deadlock.
  - A failed job loses at most the batch it has not written. `app:index:rebuild` parses those blobs again.
  - Orchestrator decisions after review: the dev worker keeps the Doctrine profiler, because the batches are enough. The worker's `--memory-limit` sits below the PHP `memory_limit`, at 96M.
  - The commit message is `fix: F12 index job memory`, as the orchestrator asked.
- **Follow-ups and new ideas:**
  - In debug mode, a repository of about 10,000 PHP files still adds about 70 MB in the dev worker, which starts a job at about 29 MB. That is close to the 128M PHP limit. A larger repository in `dev` needs the profiler off in the worker, which the orchestrator did not choose for now.
  - In `test`, the `records` test handler and the `main` fingers-crossed handler, which has no `buffer_size`, keep every `doctrine` log record of a test.
