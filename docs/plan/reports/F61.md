## Report: F61 Keyboard gutter test race

- **Status:** Done (awaiting merge). One commit `feat: F61 keyboard gutter test race` on the worktree branch `f61-keyboard-gutter-race`, from `d0a437d`.
- **Summary:**
  - The cause is the race of the scope, in the code. `CodeFile` scrolls to the line of the hash once per frame until the row is in view below the header. The row, and with it the "+" of line 100, exists one frame before the loop sees it and ends. When the test scrolled in that frame, the next move of the loop scrolled the window back and the loop then ended with `done`, so the "+" stayed in the visible code.
  - A user who scrolls while a link to a line loads was pulled back the same way, up to 60 times or for 10 s while the rows were not drawn.
  - `CodeFile` now ends the scroll to a line at the first `wheel`, `touchstart`, `pointerdown`, or `keydown` on the window, in the capture phase. `USER_INPUT_EVENTS` moved from `RequestChanges.tsx` to `assets/code/scrollTarget.ts`, so the two automatic scrolls stop on the same input.
  - The test scrolls with `PageDown`, a user input that the fix covers, instead of `window.scrollBy()` from `page.evaluate()`.
- **Proof of the cause:** a log of the loop moves and of the window scroll events in the page, read by the test after the poll, without an extra call before the test scroll (`var/f61/instrumented-6.log`, git-ignored). Load 109 to 72, 12 of 50 failed. In each of the 12 failures the test scrolled from Y 2090 to 2510, the next frame of the loop moved back to 2090, and the loop ended with `done` in the frame after. In each of the 38 passes the loop ended before the test scroll. With one more `evaluate()` call between the "+" check and the test scroll, 0 of 230 runs failed at loads 16 to 228, because the call gave the loop the frame that it needs.
- **Measurements** of the test "The gutter + outside the visible code keeps the focus that Tab gives it, and Space opens the comment box" with `--repeat-each=50` on 4 workers. - **Decisions and deviations:**
  - **User input, not a scroll that the loop did not make.** `Virtualizer.scrollFix()` of `@pierre/diffs` scrolls the window when the rendered rows differ from the estimated heights, for example with wrapped lines or annotations, and the scroll anchoring of the browser does the same when content above the code changes height. A comparison with the last Y of the loop stops the loop on those scrolls, before the line is in view. In one run of the UI suite, a log of such scrolls during the loop showed only the scroll of this test, so the suite does not show the difference.
  - **The events of `RequestChanges`.** The scope names `wheel`, `touchmove`, and scroll keys. The list of `keepInView()` in `RequestChanges.tsx` already ends an automatic scroll on `wheel`, `touchstart`, `pointerdown`, and `keydown`, so both use that one list. Any key, not only a scroll key: Tab also scrolls, to the element that gets the focus. `pointerdown` covers a click on a line number, which selects that line while the loop goes on to the line of the hash. The change to `RequestChanges.tsx` is outside the files of the scope, and only moves the constant.
  - **Capture phase.** The `InteractionManager` of `@pierre/diffs` stops the propagation of a `pointerdown` on the gutter "+", so a listener in the bubble phase does not see it.
  - **`PageDown`, not the mouse wheel.** The spec uses only the keyboard (D31). In the test, `PageDown` scrolls the window by 554 of its 720 px, so the "+" at 413 px goes above the header, and the virtualizer keeps the row rendered.
  - **The new test holds the worker.** Without it, the loop runs for about 100 ms, so a key press from the test often comes after the loop. While the worker is held, the loop runs for its 60 moves, about 1 s.
  - No retries and no longer timeout, as the scope says.
  - **Library documentation:** the `Virtualizer`, `VirtualizedFile`, and `InteractionManager` behaviour of `@pierre/diffs` 1.5.2 comes from the installed sources.
- **Follow-ups and new ideas:**
  - **The scroll to a line gives up after about 1 s, not 10 s.** Until the worker pool of the page is ready, the file has the height of its header, the page is 1093 px high, and each scroll of the loop is clamped at Y 373. Each clamped scroll counts as a move, so the loop ends after `MAXIMUM_SCROLL_MOVES` (60) frames. With the worker held for 3 s, the loop ended after 1141 ms, and when the rows came, the window stayed at Y 373 with line 1 at the top. On a loaded host, where the pool takes seconds (F55), a link to a line then shows the top of the file. This changes the candidate "Scroll to a line after 10 s": the limit that comes first is the 60 moves.
